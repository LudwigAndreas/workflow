# workflow

[🇬🇧 English](./README.md) | 🇷🇺 Русский

Эталонная конфигурация корпоративной **разработки от спецификаций**
(spec-driven development) для многорепозиторного приложения на
[OpenSpec](https://github.com/Fission-AI/OpenSpec), с проекцией на доску Jira и
управлением из **Claude Code и Qwen Code**.

Собрана под **Bitbucket Data Center + Jenkins + Argo CD**.

**Начните отсюда: [`docs/workflow.ru.md`](./docs/workflow.ru.md)** — одна
схема, пять этапов и ответ на вопрос «где источник истины».

## Идея одной картинкой

```
аналитик пишет ОДИН мастер-интент  ──▶  тимлид его вливает
                                              │
                         ┌────────────────────┼────────────────────┐
                         ▼                    ▼                    ▼
                   тестировщик пишет      backend             frontend
                   по нему тесты          реализует           реализует
                         └────────────────────┴────────────────────┘
                                              │  все репозитории закрыты
                                              ▼
                          интент архивирован → его specs И ЕСТЬ
                                               источник истины о системе
```

Одна история Jira становится одним **мастер-интентом** в общем хранилище
`specifications`: что верно сегодня, почему это должно измениться, что система
должна будет делать и какой репозиторий за какую часть отвечает. Тимлид вливает
его — и это влитие является шлюзом: до него не должно существовать ни одной
ветки.

Дальше все работают **одновременно**. Тестировщик пишет тесты по сценариям
интента до появления кода. Каждый репозиторий выводит из интента свой
OpenSpec-change и проходит собственный цикл `propose → apply → archive`.
Backend и frontend не согласуют ничего напрямую — они строят по контракту,
опубликованному интентом.

Когда все репозитории заархивировали свою работу, архивируется сам интент, и
его specs вливаются в `specifications/openspec/specs/` — базу, по которой
пишется следующий интент.

## Быстрый старт

```bash
git clone --recurse-submodules <url-этого-репозитория> workflow
cd workflow
make init          # сабмодули + регистрация общего хранилища "specifications"
make init-repos    # плюс подключение всех заготовок в src/
make status        # что сейчас в работе
make check         # удовлетворяет ли этот checkout метрике SDD?
```

**Если вы backend/frontend-разработчик**, этот репозиторий вам, скорее всего,
не нужен вовсе. Склонируйте свой репозиторий приложения и прочитайте
[`docs/roles/developer.ru.md`](./docs/roles/developer.ru.md). Этот репозиторий
нужен для написания интентов, охватывающих несколько репозиториев.

## Команды

Каждая команда есть для обоих CLI. В Claude это `/sdd:intent`, в Qwen —
`/sdd-intent`.

Своих команд всего четыре, и ни одна не подменяет стандартную команду
OpenSpec. **Разработчики работают стандартным OpenSpec, без изменений.**

| Этап | Команда | Кто |
|---|---|---|
| понять текущую систему | `/opsx:explore` | аналитик |
| написать мастер-интент | **`/sdd:intent`** | аналитик |
| проверить и утвердить | **`/sdd:review`** | тимлид |
| план тестов, до кода | **`/sdd:tests`** | тестировщик |
| вывести change репозитория | `/opsx:propose` | разработчик |
| реализовать | `/opsx:apply` | разработчик |
| закрыть change репозитория | `/opsx:archive` | разработчик |
| где что находится? | **`/sdd:status`** | любой |
| заархивировать интент | `make gate INTENT=<id>`, затем `openspec archive <id> --store specifications` | аналитик |

Стандартные команды ведут себя как процесс этой команды благодаря
`openspec/config.yaml` каждого репозитория: его `context`, `rules` и guidance в
`operations` CLI подставляет в команды по умолчанию. Локальное знание живёт как
конфигурация, а не как форкнутая команда, которая расходится с апстримом.

Копии для Qwen **генерируются** из версий Claude — правьте
`.claude/commands/sdd/` и запускайте `make commands`. `make commands-check`
роняет сборку, если они разошлись.

## Структура

```
docs/                    процесс, мастер-интент, типы работ, Jira, роли
specifications/          сабмодуль — общее хранилище; бизнес-источник истины
  openspec/specs/          как система ведёт себя сегодня
  openspec/changes/        мастер-интенты в работе
  openspec/schemas/        определение процесса master-intent
src/
  backend/               у каждого: свои openspec specs и changes, свои .claude/.qwen
  frontend/
  gitops_backend/
  gitops_frontend/
templates/repo-kit/      то, что scripts/setup-repo.sh ставит в репозиторий
scripts/
  setup-openspec.sh        регистрация хранилища; выгрузка сабмодулей
  setup-repo.sh            установка набора SDD в репозиторий приложения
  intent-status.sh         докуда дошёл каждый интент, по данным самих репозиториев
  intent-gate.sh           жёсткий шлюз перед архивацией интента
  check-sdd.sh             метрика «история следовала SDD»
  sync.sh                  подтянуть свежие общие спецификации
  gen-qwen-commands.sh     перегенерировать команды Qwen из команд Claude
```

## Метрика SDD

История засчитывается как «следовавшая SDD», когда на ней метка `SDD` и
существует ветка с её ключом. Чтобы выполнить это механически, нужно чуть
больше, и `check-sdd.sh` проверяет всё — включая единственное условие, которое
нельзя подделать: **интент был влит раньше первого коммита в любой ветке**.

```bash
make check
JIRA_URL=... JIRA_TOKEN=... make check   # плюс проверка метки через Jira
```

Без переменных Jira проверки метки *пропускаются, а не считаются пройденными*, и
скрипт об этом сообщает.

## Шлюз архивации

`openspec archive --yes` лишь **предупреждает** о незавершённом разветвлении, а
галочка — это просто символ, который кто-то напечатал. Поэтому архивация
мастер-интента проходит через шлюз, читающий сами репозитории:

```bash
make gate INTENT=<intent-id>
```

Он падает, если хоть один репозиторий из чек-листа Fan-out не заархивировал change
со ссылкой на интент, и прямо называет ложь, когда галочка утверждает больше,
чем есть на самом деле.

## Добавление репозитория

```bash
scripts/setup-repo.sh <имя> [путь]
```

Ставит стандартные команды `opsx` для обоих CLI, отрисованный
`openspec/config.yaml` с контекстом и правилами команды, и руководства для
агентов. Ни своей схемы, ни своих команд: репозиторий использует стандартный
процесс `spec-driven`. Укажите любой путь, чтобы настроить собственный клон
разработчика — обычный случай в повседневной работе.
