# Workflow аналитики / архитектуры: от задачи в Jira до смёрженного контракта

[🇬🇧 English](./analytics-workflow.md) | 🇷🇺 Русский

Это руководство на каждый день для **аналитиков, архитекторов и авторов
бизнес-предложений (product/business proposal authors)**, работающих в
multirepo-приложении. Вы работаете в **Mode A**: склонированы именно в этот
репозиторий `workflow`, где каждый прикладной репозиторий подключён как
сабмодуль рядом с остальными — это даёт полный контекст для проработки
изменения, затрагивающего несколько репозиториев. Вы **никогда** не
трогаете код в `src/*` напрямую — это работа разработчика-исполнителя.

Сначала один раз прочитайте корневой [`AGENTS.md`](../AGENTS.md) (на
английском), особенно разделы «Where a change gets authored» и «Propose vs.
plan: who writes what» — этот документ является практическим разбором той
модели.

## Единоразовая настройка

```bash
git clone --recurse-submodules <this-repo-url> workflow
cd workflow
make init      # обновление сабмодулей + локальная регистрация общего store "specifications"
make doctor    # проверка связки OpenSpec root/store
```

Перед началом любой новой работы подтягивайте актуальные общие
спецификации:

```bash
make sync      # обновляет specifications до последней версии, отчёт по сабмодулям
```

## Что относится к `specifications`, а что нет

Общий store хранит **только сквозные (cross-cutting) возможности**:
контракты, которые должны согласовать несколько репозиториев (API между
frontend и backend, общие события, всё, что публикует `common`). Он
намеренно держится небольшим.

Если задача из Jira оказывается затрагивающей только один репозиторий
(ничего, что потребляет другой репозиторий), **предлагать её не ваша
задача** — передайте её напрямую разработчику этого репозитория. Он
предложит и реализует её полностью внутри своего репозитория; у вас в этом
пути роли нет вообще.

## Жизненный цикл: задача в Jira → смёрженный контракт, готовый к планированию

**1. Разберите задачу.** Убедитесь, что она действительно вводит или меняет
   что-то, что должны согласовать несколько репозиториев. Соберите
   затронутые репозитории в единое рабочее представление вместо ручного
   переключения между директориями:
   ```bash
   openspec workset create <name>                       # сохранённое представление затронутых src/*-репозиториев
   openspec context --code-workspace ws.code-workspace   # объединённый VS Code workspace для изменения
   ```

**2. Propose (предложение).** Из этого workflow-репозитория (полный
   межрепозиторный контекст для чтения):
   ```bash
   openspec new change <name>
   ```
   Запустите `/opsx-propose` относительно `specifications`. Он
   сгенерирует `proposal.md` (зачем) и `specs/*.md` (что — наблюдаемая
   delta контракта). **Остановитесь на этом.** Не позволяйте потоку
   продолжиться до `design.md` или `tasks.md`.

   Это не просто договорённость — `specifications/openspec/config.yaml`
   объявляет `rules:` для `design` и `tasks`, которые указывают любому
   агенту здесь останавливаться после `specs` при составлении исходного
   предложения. Причина практическая, а не бюрократическая: у вас нет
   перед глазами конвенций и паттернов целевой кодовой базы, поэтому
   черновик `design.md`/`tasks.md` от вас всё равно будет переписан
   разработчиком-исполнителем. `proposal.md` + `specs/*.md` — «зачем» и
   наблюдаемое «что» — это законно ваша зона: сама схема инструкций для
   `specs` прямо говорит избегать имён классов/функций, выбора библиотек и
   шагов реализации.

**3. Откройте PR.** Запушьте ветку, откройте PR в репозиторий
   `specifications`.

**4. Ревью и утверждение.** Тех-лид / продукт ревьюит PR, с особым
   вниманием к delta контракта — frontend и backend будут потом собирать
   код против него независимо друг от друга, так что любая
   неоднозначность здесь превращается в то, что две команды решают одну и
   ту же задачу двумя разными способами. Смёржите в `main`.

**5. Передайте дальше.** Сообщите разработчикам затронутых репозиториев,
   что изменение готово к планированию. Дальше **они** пишут `design.md` и
   `tasks.md` — см. [workflow разработчика](./developer-workflow.ru.md),
   раздел «Plan». Вы их не пишете, и вам не нужно их подгонять — они могут
   обнаружить изменение сами:
   ```bash
   openspec instructions design --change <id> --store specifications --json
   openspec instructions tasks  --change <id> --store specifications --json
   ```

**6. Отслеживайте прогресс** из этого репозитория, не дожидаясь
   отдельных статус-апдейтов:
   ```bash
   openspec list   --store specifications
   openspec show   <change-id> --store specifications
   openspec status --change <change-id> --store specifications --json
   ```
   `isComplete: false` — **ожидаемое** состояние, пока разработчик не
   добавит `tasks.md`; это означает лишь «ещё не готово к apply», а не что
   что-то не так.

**7. Archive (архивирование)**, как только каждый потребляющий репозиторий
   смёржил и развернул свою часть:
   ```bash
   /opsx-archive <change-id> --store specifications
   ```
   Это перемещает изменение в `changes/archive/` и запускает `/opsx-sync`
   (интеллектуальное слияние силами агента), чтобы обновить
   `specifications/openspec/specs/*` до новой канонической истины — на неё
   будут опираться будущие предложения. Этот шаг часто инициирует тот
   разработчик, кто закончил последним, но вы тоже можете его запустить;
   в любом случае сначала убедитесь, что **все** стороны выпустили свою
   часть, а не только одна.

## Как убедиться, что предложение мёржабельно всего с двумя артефактами

`openspec validate` проходит успешно на изменении, содержащем только
`proposal.md` + `specs/` — `design`/`tasks` отображаются как
`"blocked"`/`"ready"`, а не как ошибки. Это значит, что вы можете спокойно
открыть и смёржить PR в `specifications`, имея только бизнес-предложение;
не нужно ждать или имитировать `design.md`/`tasks.md`, чтобы его смёржить.

## Использование ИИ в повседневной работе

И Claude Code (`.claude/commands/opsx-*`), и Qwen
(`.qwen/commands/opsx-*`) предоставляют одни и те же слэш-команды из
корня этого репозитория:

| Команда | Когда использовать |
|---|---|
| `/opsx-explore` | Проговорить с агентом задачу вслух на этапе проработки — артефакты ещё не создаются, безопасно использовать до того, как вы в чём-либо уверены |
| `/opsx-propose` | Сгенерировать `proposal.md` + delta контракта `specs/*.md` из описания; дать потоку остановиться перед `design`/`tasks` |
| `/opsx-update` | Пересмотреть proposal/specs после фидбека от ревью, сохраняя согласованность `proposal.md` и `specs/*.md` между собой |
| `/opsx-sync` | Слить delta-спецификации в основные specs — автоматически запускается внутри `/opsx-archive`, либо отдельно, если нужно раньше отразить изменение в основных specs |

## Чего делать нельзя

- **Не пишите `design.md` или `tasks.md`**, даже если уверены, что знаете
  правильный технический подход — это прямо зона ответственности
  разработчика-исполнителя, и правила в
  `specifications/openspec/config.yaml` предписывают любому агенту здесь
  останавливаться перед этими артефактами.
- **Не трогайте код `src/*` напрямую.** Ваш результат — это `proposal.md` +
  `specs/*.md`; всё, что после, — работа разработчика.
- **Не кладите репозиторно-локальные (не контрактные) спецификации в
  `specifications`.** Держите общий store маленьким — локальные для
  репозитория вопросы относятся к его собственному `openspec/specs/`, а
  не сюда.
- **Не архивируйте общее изменение, пока не выпустился каждый
  потребляющий репозиторий.** Ранняя архивация обновляет каноническую
  спецификацию до того, как контракт стал реальностью повсюду.

## Шпаргалка

```bash
# настройка (один раз)
make init && make doctor

# перед началом новой работы
make sync

# проработать межрепозиторное изменение
openspec workset create <name>
openspec context --code-workspace ws.code-workspace

# предложить (остановиться после specs)
openspec new change <name>
/opsx-propose

# отслеживать
openspec list   --store specifications
openspec show   <change-id> --store specifications
openspec status --change <change-id> --store specifications --json

# закрыть (после того как выпустились все стороны)
/opsx-archive <change-id> --store specifications
```
