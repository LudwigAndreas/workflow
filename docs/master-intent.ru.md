# Мастер-интент

[🇬🇧 English](./master-intent.md) | 🇷🇺 Русский

**Мастер-интент** — это полное бизнес-описание одного изменения: одна история
Jira, один OpenSpec-change в хранилище `specifications`, четыре артефакта.

Он существует, чтобы тестировщик и несколько разработчиков могли начать работу
одновременно, по одному документу, не согласовывая ничего между собой. Планка
высокая: всё, что разработчику нужно, но чего он здесь не найдёт, превратится в
вопрос в чате, а решение, принятое в чате, не видит больше никто.

## Анатомия

```
specifications/openspec/changes/<intent-id>/
├── .openspec.yaml     schema, jira: PROJ-123
├── analysis.md        что верно сегодня
├── proposal.md        зачем, что меняется, порядок раскатки
├── specs/
│   └── <capability>/spec.md    контракт поведения
└── handoff.md         обязательства по репозиториям + чек-лист разветвления
```

### `analysis.md` — что верно сегодня

Только описание. Как только вы пишете, что система *должна* делать, вы уже в
`proposal.md`.

| Раздел | Содержит |
|---|---|
| Scope | какая capability рассматривается и на какой вопрос надо ответить |
| Current behaviour | что происходит сегодня, со ссылками на specs и пути к файлам |
| Components involved | каждый участвующий репозиторий — **включая те, что не меняются** |
| Contracts in play | каждый интерфейс, от которого зависит >1 репозиторий, с поставщиком и всеми потребителями |
| Constraints | что ограничивает решение и не обсуждается, с источником ограничения |
| Unknowns | на что вы не смогли ответить, с владельцем вопроса и тем, что он блокирует |

Два правила, дающие большую часть пользы:

- **Ссылайтесь на источник везде.** Утверждение без имени spec или пути к файлу
  — догадка, а догадка здесь повторяется как факт каждым разработчиком ниже по
  потоку.
- **Никогда не выдумывайте ответ, чтобы закрыть неизвестность.** Неизвестность,
  поднятая здесь, стоит одного предложения. Она же, найденная во время
  реализации, стоит переоткрытой истории.

Перечисление репозиториев, которые *не* меняются, важнее, чем кажется: оно
говорит разработчику, что область рассмотрели и исключили, а не забыли.

### `proposal.md` — зачем и что меняется

Раздел **Rollout order** — единственное, что может содержать только этот
документ. Общее хранилище — единственный корень, который видит все репозитории
сразу, поэтому только здесь можно зафиксировать порядок между ними. Он должен
говорить:

- какой репозиторий поставляет изменённый контракт и, значит, ложится и
  публикуется **первым**
- какие репозитории независимы друг от друга и потому идут **параллельно** —
  обычно backend и frontend, как только контракт согласован

Таблица **Affected repositories** задаёт `handoff.md`. Меняете одно — меняйте
и другое.

### `specs/` — контракт поведения

Самый читаемый артефакт процесса. Тестировщик пишет по нему тесты до появления
кода; каждый разработчик реализует по нему.

**Уровень.** Включайте поведение, наблюдаемое на границе системы, и контракты,
о которых должны договориться несколько репозиториев. Исключайте всё, что
наблюдаемо только внутри одного репозитория, — это компонентная spec
разработчика.

> Быстрая проверка: если реализацию можно свободно изменить, не меняя ничего
> наблюдаемого снаружи, — этому здесь не место.

**Механика, которая ломается молча** — это стоит проверять руками:

- Сценарии пишутся **ровно четырьмя решётками** (`#### Scenario:`). Три
  решётки или список маркеров разбираются как *ничто*, без ошибки, и требование
  выглядит бессценарным для всех инструментов ниже по потоку.
- Новые capability начинаются с `## Purpose`, 50+ символов. Без него архивация
  оставит в постоянной spec заглушку `TBD ... Update Purpose after archive`.
- Для требований `MODIFIED` копируйте **весь** существующий блок вместе со
  всеми сценариями, и только потом правьте. Частичная копия молча удаляет
  пропущенные сценарии при архивации интента.

**Качество сценариев.** `WHEN` — конкретный внешний триггер: «когда
пользователь отправляет форму с истёкшим токеном», а не «когда пользователь не
авторизован». `THEN` наблюдаем снаружи: код ответа, показанное сообщение,
сохранённая запись, отправленное событие. Никогда — «сервис знает».

У каждого требования должен быть хотя бы один **несчастливый путь**. Интент,
где все сценарии счастливые, не готов к ревью, и это самая частая причина
вернуть его автору.

### `handoff.md` — кто какую часть реализует

То, что делает возможной параллельную работу. Для каждого репозитория:

| Поле | Должно содержать |
|---|---|
| Requirements owned | точные имена `### Requirement:` из `specs/` |
| Contract obligations | достаточно точно, чтобы строить **до появления второй стороны** |
| Depends on | какие репозитории должны опубликоваться раньше, либо «ничего — можно начинать сразу» |
| Acceptance | как разработчик поймёт, что закончил, — проверяемо без чтения кода |
| Guidance | только то, до чего компетентный разработчик там не додумается сам |

Затем чек-лист:

```markdown
## Fan-out

- [ ] backend (PROJ-124) - derived change archived
- [ ] frontend (PROJ-125) - derived change archived
```

**Два инварианта.**

1. Каждое требование в `specs/` принадлежит хотя бы одному репозиторию.
   Посчитайте объединение и проверьте — требование без владельца это и есть
   способ выпустить историю наполовину реализованной.
2. Каждая галочка начинается снятой и ставится только скриптом
   `scripts/intent-gate.sh --tick`, который проверяет, что репозиторий
   действительно заархивировал работу. Галочка, проставленная руками, — ровно
   то, ради чего шлюз и создан.

«Возвращает данные пользователя» — не обязательство по контракту. Имена полей,
типы, коды ответов и случаи ошибок — да. Описывайте здесь с запасом:
разработчик по ту сторону не может у вас спросить, потому что работает
одновременно с вами.

## Уровни, одной таблицей

| Где | Содержит | Пишет |
|---|---|---|
| `specs/` интента | поведение на границе системы, межрепозиторные контракты | аналитик |
| `handoff.md` интента | кто чем владеет, обязательства по контракту | аналитик |
| `specs/` репозитория | поведение на границе одного репозитория | разработчик |
| `design.md` репозитория | как — классы, библиотеки, схемы, раскладка файлов | разработчик |
| `tasks.md` репозитория | чек-лист | разработчик |

`design.md` — первое место, где допустимы детали реализации, и единственное.
Конфигурация хранилища активно отказывает в `design.md` и `tasks.md` и велит
агенту остановиться, а не создавать их.

Разделение намеренное: аналитик вправе писать *зачем* и *что*, но не *как* —
для этого нужно знание кодовой базы и принятых в ней практик, которого у него
нет.

## Жизненный цикл

```
написан ──▶ проверен ──▶ влит ──▶ разветвлён ──▶ все репозитории закрыты ──▶ архивирован
   │           │           │                                                     │
аналитик   тимлид    шлюз очерёдности:                        specs вливаются в
                     до этого не должно                specifications/openspec/specs/
                     существовать ветки                 = новый источник истины
```

После архивации specs интента *становятся* описанием системы. `analysis.md`
следующего интента будет на них ссылаться. Ранняя архивация — до того как
закончили все репозитории — публикует описание несуществующего поведения, и
каждый написанный после этого интент наследует ошибку. Отсюда и шлюз.

## Проверка интента

```bash
openspec validate <intent-id> --store specifications --strict
scripts/check-sdd.sh --change <intent-id> --store specifications
scripts/intent-status.sh <intent-id>      # докуда дошло разветвление
scripts/intent-gate.sh <intent-id>        # можно ли уже архивировать?
```
