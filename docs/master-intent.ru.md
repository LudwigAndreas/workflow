# Мастер-интент

[🇬🇧 English](./master-intent.md) | 🇷🇺 Русский

**Мастер-интент** — это бизнес-описание одного изменения: одна история Jira,
один OpenSpec-change в хранилище `specifications`, два артефакта. И это
**мета-слой над стандартным процессом OpenSpec**, а не его вариант.

В этом различии вся суть. Аналитик пишет интент; каждый разработчик затем
подаёт его на вход *неизменённому* процессу OpenSpec у себя в репозитории и сам
пишет по нему свои `proposal.md`, `specs/`, `design.md` и `tasks.md`.

```
      АНАЛИТИК                        РАЗРАБОТЧИК, в одном репозитории
  ┌────────────────┐              ┌──────────────────────────────────┐
  │  мастер-интент │   вход для   │ /opsx:propose                    │
  │   intent.md    │ ───────────▶ │ /opsx:apply                      │
  │   specs/       │   propose    │ /opsx:archive                    │
  └────────────────┘              └──────────────────────────────────┘
   бизнес-потребность               proposal.md, specs/, design.md,
   общесистемный контекст           tasks.md — всё пишет и всем владеет
   бизнес-правила                   разработчик
```

Интент — это **вход** для propose. Он никогда не является его половиной.
Разрезать один процесс OpenSpec между двумя ролями — аналитик пишет proposal,
разработчик пишет tasks — это ровно то, ради чего этот слой и существует: так
меняется уже связно спроектированный процесс, и каждая роль остаётся с
фрагментом документа, которым не владеет ни одна из них.

Интент существует, чтобы тестировщик и несколько разработчиков могли начать
одновременно, по одному документу, не согласовывая ничего между собой. Планка
высокая: всё, что разработчику нужно, но чего здесь нет, превращается в вопрос
в чате, а ответ в чате — это решение, которого больше никто не видит.

## Устройство

```
specifications/openspec/changes/<intent-id>/
├── .openspec.yaml     schema: master-intent, jira: PROJ-123
├── intent.md          бизнес-потребность, общесистемный контекст, разветвление
└── specs/
    └── <capability>/spec.md    бизнес-правила, которые меняет это изменение
```

### `intent.md` — бизнес-потребность и общесистемный контекст

| Раздел | Содержит |
|---|---|
| Бизнес-потребность | зачем это нужно, чью проблему решает, что будет, если не делать |
| Сегодня | как эта возможность работает для бизнеса сейчас, со ссылками на источники |
| Что должно стать правдой | бизнес-результат, наблюдаемый пользователем или другой организацией |
| Общесистемный контекст | внешние API-контракты, нужный интерфейс, обязательства по данным, события |
| Репозитории | кто участвует и что вносит — **включая исключённые** |
| Ограничения | что сужает пространство решений и не обсуждается, с источником |
| Открытые вопросы | на что не нашли ответа: владелец и что это блокирует |
| Fan-out | по одной непроставленной галочке на репозиторий |

**Общесистемный контекст — тот раздел, ради которого этот слой и нужен.** Всё
остальное в интенте, при желании, мог бы написать разработчик из одного
репозитория; это — нет. Здесь то, чего требует внешний мир: внешние
API-контракты, которые система предоставляет или потребляет, включая формы,
уже зафиксированные партнёром; что пользователь должен видеть и уметь сделать;
какие данные нужно собирать или хранить; какие события нужны другим сторонам.
Приложите или дайте ссылку на сами документы внешних контрактов, если они есть.

Это контекст, а не дизайн. Пишите, чего требует внешний мир, и никогда — как
систему следует под это построить.

Три правила несут большую часть пользы:

- **Ссылайтесь на источники в разделе «Сегодня».** Утверждение без
  бизнес-правила или пути к файлу — догадка, а догадка здесь повторяется как
  факт каждым разработчиком ниже по потоку.
- **Никогда не закрывайте открытый вопрос выдуманным ответом.** Неизвестность,
  поднятая здесь, стоит одного предложения. Она же, найденная при реализации,
  стоит переоткрытой истории.
- **Никогда не пишите, что репозиторий должен построить.** Таблица
  «Репозитории» говорит, что каждый *вносит*, в терминах бизнеса. Что он
  строит, решает его собственный `propose` — разработчиком, который им владеет.

Перечислять репозитории, которые НЕ изменятся, важнее, чем кажется: это
говорит разработчику, что область рассмотрели и исключили, а не забыли.

### `specs/` — бизнес-правила

Самый читаемый артефакт процесса. Тестировщик пишет по нему тесты до появления
кода; `propose` каждого разработчика выводит из него требования своего
репозитория. При архивации он вливается в `specifications/openspec/specs/` и
становится действующим описанием бизнеса.

**Уровень абстракции.** Включайте правила, наблюдаемые пользователем, клиентом
или другой организацией, и правила, о которых должны договориться несколько
репозиториев. Исключайте всё, что наблюдаемо только внутри одного репозитория —
это компонентная спецификация разработчика, пишется у него в репозитории во
время `propose`.

> Быстрая проверка: если реализацию можно свободно изменить, ничего не поменяв
> снаружи, — этому здесь не место.

**Механика, которая ломается молча** — проверяйте руками:

- Сценарии — **ровно четыре решётки** (`#### Scenario:`). Три решётки или
  список пунктов парсятся как *ничто*, без ошибки, и требование выглядит
  бессценарным для всех инструментов ниже по потоку.
- Новые capability открываются разделом `## Purpose` от 50 символов. Без него
  архивация оставит в постоянной спецификации заглушку
  `TBD ... Update Purpose after archive`.
- Для `MODIFIED`-требований копируйте **весь** существующий блок вместе со
  всеми сценариями, затем правьте. Частичная копия молча удаляет пропущенные
  сценарии при архивации.

**Качество сценариев.** `WHEN` — конкретное внешнее событие: «когда
пользователь отправляет форму с истёкшим токеном», а не «когда пользователь не
авторизован». `THEN` — наблюдаемо снаружи: код ответа, показанное сообщение,
сохранённая запись, отправленное событие. Никогда «сервис знает».

У каждого требования должен быть хотя бы один **несчастливый путь**. Интент,
где все сценарии счастливые, не готов к ревью — и это самая частая причина
вернуть его автору.

Интент, не меняющий ни одного наблюдаемого бизнес-правила, законно не имеет
specs вовсе — поставьте `skip_specs: true`, а не выдумывайте требование ради
прохождения валидации.

### Чек-лист разветвления

```markdown
## Fan-out

- [ ] `backend` (`PROJ-124`) - change archived
- [ ] `frontend` (`PROJ-125`) - change archived
```

**Два инварианта.**

1. Каждое требование в `specs/` очевидно относится хотя бы к одному
   репозиторию из таблицы. Требование, за которое не отвечает никто, — это то,
   как история уезжает наполовину сделанной.
2. Все галочки начинают непроставленными и ставятся только
   `scripts/intent-gate.sh --tick`, который проверяет, что репозиторий
   действительно заархивировал работу. Галочка, поставленная руками, — ровно
   то, что шлюз и ловит.

## Уровни абстракции, одной таблицей

| Где | Содержит | Пишет |
|---|---|---|
| интент `intent.md` | бизнес-потребность, общесистемный контекст, кто участвует | аналитик |
| интент `specs/` | бизнес-правила — что наблюдает пользователь или другая организация | аналитик |
| репозиторий `proposal.md` | что делает **этот** репозиторий | разработчик |
| репозиторий `specs/` | поведение на границе одного репозитория | разработчик |
| репозиторий `design.md` | как — классы, библиотеки, схемы, раскладка файлов | разработчик |
| репозиторий `tasks.md` | чек-лист | разработчик |

Схема хранилища определяет ровно два артефакта, поэтому запрос третьего — это
жёсткая ошибка, а не договорённость:

```
$ openspec instructions proposal --change <id> --store specifications
Artifact 'proposal' not found in schema 'master-intent'. Valid artifacts:
  intent
  specs
```

`design.md` — первое и единственное место, где допустимы детали реализации.
Разделение сознательное: аналитик может обоснованно установить
бизнес-потребность и внешние ограничения, но не *что строить* — для этого нужно
знание кодовой базы и принятых практик, которого у него нет, и решает это
собственный proposal разработчика.

## Жизненный цикл

```
написан ──▶ проверен ──▶ влит ──▶ разветвление ──▶ все репозитории закрыты ──▶ архив
   │           │           │                                                    │
аналитик    тимлид    шлюз очерёдности:                     бизнес-правила вливаются в
                      до влития ветки                  specifications/openspec/specs/
                      существовать не могут              = новый источник истины
```

После архивации specs интента *и есть* действующие бизнес-правила. Раздел
«Сегодня» следующего интента будет ссылаться на них. Ранняя архивация — до того
как закончили все репозитории — публикует описание поведения, которого нет, и
каждый следующий интент наследует эту ошибку. Отсюда и шлюз.

## Проверка интента

```bash
openspec validate <intent-id> --store specifications --strict
scripts/check-sdd.sh --change <intent-id> --store specifications
scripts/intent-status.sh <intent-id>      # где разветвление
scripts/intent-gate.sh <intent-id>        # можно ли уже архивировать?
```
