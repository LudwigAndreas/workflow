# Процесс

[🇬🇧 English](./workflow.md) | 🇷🇺 Русский

Одна история, один **мастер-интент**, несколько репозиториев, реализующих его
параллельно. Эта страница — основа: прочитайте её первой, затем страницу
[своей роли](./roles/).

## Общая схема

```
                    ┌─────────────────────────────────────────┐
                    │  specifications  (бизнес-истина)         │
   аналитик ───1──▶ │  мастер-интент: analysis, proposal,      │
                    │  specs, handoff                          │
   тимлид ────2──▶  │  проверен, влит  ◀── шлюз очерёдности    │
                    └───────────────┬─────────────────────────┘
                                    │  разветвление, параллельно
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
        3  тестировщик          4  backend            4  frontend
        пишет тесты             derive → plan         derive → plan
        по specs                → apply → archive     → apply → archive
              │                     │                     │
              └─────────────────────┴─────────────────────┘
                                    │  все репозитории закрыты
                                    ▼
                    ┌─────────────────────────────────────────┐
                    │  5  интент архивирован                   │
                    │  его specs становятся openspec/specs/ —  │
                    │  базой, относительно которой пишется     │
                    │  каждый следующий интент                 │
                    └─────────────────────────────────────────┘
```

## Пять этапов

### 1. Аналитик пишет мастер-интент

Аналитик изучает текущий источник истины стандартной командой `/opsx:explore`,
затем создаёт один мастер-интент в хранилище `specifications` командой
`/sdd:intent`. Этот шаг — **единственная** нестандартная команда во всём
процессе: он охватывает сразу все репозитории, чего не делает ни одна
стандартная команда. Результат — один OpenSpec-change с четырьмя артефактами:

| Артефакт | Отвечает на вопрос | Уровень |
|---|---|---|
| `analysis.md` | Что верно **сегодня**? | только описание, всё со ссылками на источники |
| `proposal.md` | Зачем, что меняется, в каком порядке | системный: репозитории, capabilities, контракты |
| `specs/` | Что система **должна делать**? | наблюдаемое поведение + межрепозиторные контракты |
| `handoff.md` | Кто какую часть реализует? | обязательства по репозиториям + чек-лист разветвления |

Аналитик никогда не пишет `design.md` и `tasks.md`. Конфигурация хранилища
запрещает их: технический дизайн требует знания кодовой базы, которого у
аналитика нет, и принадлежит разработчику, который будет это реализовывать.

### 2. Тимлид проверяет и вливает

`/sdd:review`. Это ключевой шлюз всего процесса, потому что после него
несколько человек начнут строить по этому документу, **не разговаривая друг с
другом**. Расплывчатый контракт здесь будет истолкован в каждом репозитории
по-своему, и расхождение всплывёт на интеграции.

**Ни в одном репозитории не должно существовать ветки до этого влития.**
Метрика SDD фиксирует, легла ли спецификация раньше первого коммита, и это
нельзя исправить задним числом.

### 3. Тестировщик пишет тесты — сразу, а не потом

`/sdd:tests`. Сценарии в `specs/` уже записаны в форме WHEN/THEN именно для
того, чтобы их можно было исполнить как тесты до появления реализации.
Тестировщик не ждёт разработчиков: он работает по тому же контракту в то же
время.

Написание тестов также вскрывает дефекты контракта, пока они дёшевы: `THEN`,
который нельзя наблюдать снаружи; требование только со счастливым путём;
контракт, слишком размытый, чтобы написать по нему проверку.

### 4. Разработчики реализуют — параллельно и стандартными командами

Каждый затронутый репозиторий проходит полный цикл OpenSpec у себя,
**стандартными** командами. На этой стороне нет ни своей команды, ни своей
схемы:

```
git checkout -b PROJ-123/PROJ-124-<slug>    только после влития интента
/opsx:propose             proposal.md + specs/ + design.md + tasks.md,
                          с записью jira: и intent: в .openspec.yaml
/opsx:apply               работа по чек-листу
/opsx:archive             влить specs этого репозитория в openspec/specs/
```

Стандартные команды ведут себя как процесс этой команды благодаря
`openspec/config.yaml` репозитория: его `context`, `rules` и guidance в
`operations` подставляются в команды по умолчанию через `openspec
instructions`. Поэтому агент сначала читает мастер-интент, записывает обратную
ссылку и держит уровень абстракции своего репозитория — и никому не приходится
форкать команду, которая потом разойдётся с апстримом OpenSpec.

Backend и frontend идут **одновременно**, опираясь на контракт, опубликованный
в `handoff.md`. Ради этого контракт и описывается достаточно точно, чтобы по
нему можно было строить до появления второй стороны.

Порядок раскатки в `proposal.md` интента говорит, кто может начинать сразу, а
кто ждёт, пока поставщик контракта опубликует свою часть.

### 5. Интент архивируется и становится источником истины

Как только **каждый** репозиторий заархивировал свой change, архивируется сам
мастер-интент: `openspec archive <intent-id> --store specifications`. Его specs
вливаются в `specifications/openspec/specs/` — базу, относительно которой
пишется каждый следующий интент и которую первой читают при изучении системы.

Это защищено шлюзом, и шлюз — не сам CLI:

```bash
scripts/intent-gate.sh <intent-id>
```

Он проверяет по самим репозиториям, что у каждого названного в `handoff.md`
есть **заархивированный** change со ссылкой назад. `openspec archive --yes`
лишь *предупреждает* о незавершённом разветвлении и продолжает — именно
поэтому шлюз и существует.

## Источник истины — шесть вопросов, шесть ответов

| Вопрос | Единственный источник | Расположение |
|---|---|---|
| Что система делает **сегодня**? | общие specs | `specifications/openspec/specs/` |
| Что меняем **дальше** и зачем? | мастер-интент | `specifications/openspec/changes/<id>/` |
| Какая часть **моя**? | handoff | `handoff.md` этого интента |
| Как ведёт себя **один репозиторий**? | компонентные specs | `src/<repo>/openspec/specs/` |
| **Как** это здесь построено? | design + tasks | `src/<repo>/openspec/changes/<id>/` |
| **Кто** и **когда** делает? | Jira | Story / Task |

Jira никогда не хранит текст требований; specs никогда не хранят исполнителей
и спринты. Единственные ссылки через границу — `jira:` и `intent:` в
`.openspec.yaml`.

Истина о поведении намеренно **не** централизована полностью. Межрепозиторные
контракты живут в общем хранилище, потому что о них должны договориться
несколько команд. Всё остальное живёт рядом с кодом, который описывает, — и
потому проверяется в том же pull request и не может разойтись с кодом.

## Два режима работы

**Режим A — межрепозиторное авторство.** Аналитики, тимлиды и архитекторы
работают в репозитории `workflow`, где хранилище и все репозитории приложения
выгружены рядом, чтобы интент, охватывающий backend и frontend, можно было
корректно очертить.

**Режим B — реализация.** Разработчики и тестировщики работают внутри **одного**
репозитория приложения, с IDE и агентом, укоренёнными там. Ни репозиторий
workflow, ни чужие репозитории на диске не нужны. `--store specifications`
достаёт интент откуда угодно.

## Почему мастер-интент, а не отдельный change на репозиторий

Он решает сразу три проблемы:

1. **Параллельной работе нужен согласованный контракт.** Если backend и
   frontend напишут по своему proposal, контракт будет согласован дважды и
   по-разному. Здесь он согласован один раз, до того как кто-либо начал.
2. **Бизнес-намерение не привязано к репозиторию.** «Пользователь входит через
   SSO» — одно решение. Разбив его по репозиториям, вы теряете то, что
   собственно было решено.
3. **История — та единица, которую измеряет компания.** Одна история, один
   интент, одна метка `SDD` — см. [Jira ↔ SDD](./jira-sdd-mapping.ru.md).

А почему при этом остаются change в репозиториях: технический дизайн специфичен
для репозитория, должен проверяться людьми, владеющими этим кодом, и обязан
лежать в том же pull request, что и код. Единое центральное хранилище с
дизайном всех репозиториев перестаёт проверяться вместе с кодом и расходится с
ним за недели.

## Где создаётся change

| Работа | Где |
|---|---|
| Из-за этого должен измениться другой репозиторий | мастер-интент в `specifications` |
| Меняются только внутренности этого репозитория, наблюдаемое поведение системы прежнее | локальный change в этом репозитории, без интента |

Проверка: **должен ли другой репозиторий изменить свой код из-за этого?** Если
нет — работа локальная; см. [типы работ](./work-types.ru.md), где описана
дорожка для каждого вида работы, а не только для фич.

## Команды

Оба CLI, одни и те же инструкции:

| | Claude Code | Qwen Code | Откуда |
|---|---|---|---|
| Изучить текущую истину | `/opsx:explore` | `/opsx-explore` | стандартная |
| Написать интент | `/sdd:intent` | `/sdd-intent` | **своя** |
| Проверить интент | `/sdd:review` | `/sdd-review` | **своя** |
| План тестов по интенту | `/sdd:tests` | `/sdd-tests` | **своя** |
| Создать change репозитория | `/opsx:propose` | `/opsx-propose` | стандартная |
| Реализовать | `/opsx:apply` | `/opsx-apply` | стандартная |
| Завершить change репозитория | `/opsx:archive` | `/opsx-archive` | стандартная |
| Где что находится? | `/sdd:status` | `/sdd-status` | **своя** |
| Заархивировать интент | `openspec archive <id> --store specifications` | то же | стандартная, за `make gate` |

Своих команд четыре, и ни одна из них не подменяет стандартную: это шаг
кросс-репозиторного авторства и три ролевых процесса вокруг него. Внутри
репозитория приложения разработчик пользуется только стандартными командами
OpenSpec — `/opsx:propose`, `/opsx:apply`, `/opsx:archive`, а при необходимости
`/opsx:explore`, `/opsx:sync` и `/opsx:update`.

Копии для Qwen **генерируются** из версий Claude скриптом
`scripts/gen-qwen-commands.sh`. Правьте `.claude/commands/sdd/` и запускайте
его заново; `make commands-check` роняет сборку, если они разошлись.
