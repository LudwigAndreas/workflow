# Workflow разработчика: от задачи в Jira до продакшена

[🇬🇧 English](./developer-workflow.md) | 🇷🇺 Русский

Это руководство на каждый день для **frontend-, backend-, common-, gitops- и
nginx-инженеров**. Вы работаете в **Mode B**: у вас склонирован ровно один
репозиторий приложения, и ваш IDE/агент запущен из него. Вам **не нужен**
этот репозиторий `workflow`, и вам не нужно иметь на диске репозитории
других команд.

Если вы ещё не читали, сначала откройте `README.md` своего репозитория и
корневой [`AGENTS.md`](../AGENTS.md), раздел «Two roles» — это документ
исходит из той же модели и лишь добавляет практическую, пошаговую версию.

## Единоразовая настройка машины

Клонируйте только свой собственный репозиторий — не этот workflow-репозиторий:

```bash
git clone git@github.com:your-org/<frontend|backend|...>.git
cd <your-repo>
```

Зарегистрируйте общий store `specifications` один раз на машину (не на
репозиторий, и это не коммитится в git):

```bash
git clone git@github.com:LudwigAndreas/specifications.git ~/dev/specifications
openspec store register ~/dev/specifications --id specifications
```

Проверьте, что он виден отовсюду:

```bash
openspec store list --json
```

Теперь обычные команды `openspec` (без флага) работают с `openspec/specs` +
`openspec/changes` **вашего собственного репозитория**. Добавление
`--store specifications` даёт доступ к общему межрепозиторному store прямо
из вашего репозитория, без необходимости что-либо ещё клонировать.

## Две формы задач

Каждая задача из Jira, которую вы берёте в работу, попадает в один из двух
типов. Разберитесь, какой именно, **до** того как открывать OpenSpec:

| | Затрагивает только ваш репозиторий | Затрагивает контракт, который использует другой репозиторий |
|---|---|---|
| Пример | Рефакторинг внутреннего сервиса, багфикс, локальная фича | Новый/изменённый API между frontend и backend, общее событие, всё, что публикует `common` |
| Где предлагается (`propose`) | В вашем репозитории, без флага `--store` | В store `specifications` — пишет аналитика/архитектура, не вы |
| Кто пишет `proposal.md` + `specs/*.md` | Вы | Аналитика (см. [workflow аналитики](./analytics-workflow.ru.md)) |
| Кто пишет `design.md` + `tasks.md` | Вы | Вы — всегда, независимо от того, кто писал proposal |

Если оказывается, что задаче нужен новый или изменённый контракт, а
соответствующего proposal в `specifications` ещё нет — не пишите контрактную
спецификацию сами, попросите аналитику/архитектуру сначала оформить её (у
них есть межрепозиторный контекст, чтобы согласовать контракт корректно).
Если сразу перейти к `design.md`/`tasks.md` по ещё не согласованному
контракту, работу потом придётся переделывать.

## Жизненный цикл: задача в Jira → продакшен

**1. Разберите задачу.** Определите, к какому типу из таблицы выше она
   относится. Для изменения контракта проверьте, не предложила ли его уже
   аналитика:
   ```bash
   openspec list --store specifications
   ```
   Если подходящего предложения нет — подключите аналитику, прежде чем
   начинать.

**2. Propose** *(только для локальных задач — для контрактных изменений
   этот шаг пропускается, аналитика уже сделала его)*:
   ```bash
   openspec new change <name>
   ```
   Запустите `/opsx-propose` (или управляемый поток создания артефактов),
   чтобы сгенерировать `proposal.md` и `specs/*.md` для своего репозитория.
   Правила `openspec/config.yaml` вашего репозитория остановят агента перед
   `design.md`/`tasks.md` — это ожидаемо, не баг; вы напишете их следующим
   шагом, непосредственно перед реализацией.

**3. Plan (планирование).** Всегда ваша задача — независимо от того,
   пришло ли предложение от вас (локальное) или от аналитики (общий
   контракт):
   ```bash
   openspec instructions design --change <id> [--store specifications] --json
   openspec instructions tasks  --change <id> [--store specifications] --json
   ```
   Используйте связанный с `/opsx-apply` поток или своего агента, чтобы
   составить `design.md` (если изменение достаточно сложное, чтобы его
   оправдать) и `tasks.md`, опираясь на реальный код и конвенции своего
   репозитория.

   **Для межрепозиторного/контрактного изменения** разбейте `tasks.md` на
   секции по репозиториям — `## Common`, `## Backend`, `## Frontend`,
   `## GitOps` — и настройте шлюзование так, чтобы секция `## Common`
   попадала в репозиторий и её пакет публиковался *до* начала секций
   `## Backend`/`## Frontend`. Запушьте этот коммит планирования в
   `specifications` для лёгкого ревью до того, как кто-либо начнёт писать
   код — это позволяет выявить неверный технический подход или неверное
   шлюзование на раннем этапе.

**4. Apply (реализация).**
   - Если ваша задача зависит от контракта `common`, дождитесь, пока
     разработчик `common` опубликует новую версию пакета, и только потом
     обновите на неё свою зависимость.
   - Запустите `/opsx-apply` (skill `openspec-apply-change`), чтобы пройти
     `tasks.md` сверху вниз вместе с агентом. Он отмечает каждую задачу
     `[x]` по мере выполнения и останавливается на всём неоднозначном — не
     позволяйте ему угадывать при неясных требованиях.
   - Дальше следуйте обычному процессу разработки своей команды: ветка,
     PR в **свой собственный репозиторий**, код-ревью, CI, merge. Этот
     workflow-репозиторий не диктует эту часть — она такая, какую уже
     использует ваша команда.

**5. Deploy (развёртывание).** Смёрженный код доезжает до продакшена через
   обычные CI/CD вашего репозитория и репозитории `gitops_frontend` /
   `gitops_backend` (манифесты и пайплайны деплоя). Когда эти репозитории
   станут реальными (см. `scripts/add-repo.sh`), у них будет свой локальный
   `openspec/`, как и у вашего репозитория, для любых спецификаций
   поведения деплоя, которые стоит зафиксировать.

**6. Archive (архивирование).** Как только изменение смёржено и
   развёрнуто:
   ```bash
   /opsx-archive <change-id>          # локальное изменение
   /opsx-archive <change-id> --store specifications   # общий контракт
   ```
   Это перемещает изменение в `changes/archive/` и для общих изменений
   синхронизирует основные `specs/*` в `specifications`, отражая новую
   каноническую истину. **Для контрактного изменения дождитесь, пока
   каждый потребляющий репозиторий (frontend и backend) не выпустит свою
   часть**, прежде чем архивировать — не архивируйте, как только готова
   только ваша половина.

**7. Проверяйте статус в любой момент, не покидая свой репозиторий:**
   ```bash
   openspec list   --store specifications
   openspec show   <change-id> --store specifications
   openspec status --change <change-id> --store specifications --json
   ```
   `isComplete: false` в общем изменении означает лишь, что где-то ещё не
   написан `tasks.md` — это не ошибка.

## Использование ИИ в повседневной работе

И Claude Code (`.claude/commands/opsx-*`), и Qwen
(`.qwen/commands/opsx-*`) предоставляют одни и те же слэш-команды —
используйте ту, к которой подключён ваш IDE/агент:

| Команда | Когда использовать |
|---|---|
| `/opsx-explore` | Проговорить требования или технический подход с агентом, прежде чем фиксировать план — артефакты ещё не создаются |
| `/opsx-propose` | Начать локальное изменение (proposal + specs); для общего контракта — прочитать то, что уже предложила аналитика |
| `/opsx-update` | Пересмотреть proposal/design/tasks после изменения решения, сохраняя согласованность артефактов между собой |
| `/opsx-apply` | Пройти `tasks.md` от начала до конца вместе с агентом, по одной задаче за раз |
| `/opsx-sync` | Слить delta-спецификации в основные specs (автоматически запускается внутри `/opsx-archive`, можно запускать и отдельно) |
| `/opsx-archive` | Закрыть завершённое, развёрнутое изменение |

## Чего делать нельзя

- **Не пишите `proposal.md`/`specs/*.md` для межрепозиторного контракта
  самостоятельно.** Это зона ответственности аналитики — подключайте их,
  вместо того чтобы угадывать контракт самим.
- **Не подключайте `common` как сабмодуль во frontend или backend.**
  Зависите от опубликованной версии пакета и обновляйтесь осознанно —
  сабмодуль заставил бы обе стороны двигаться в лок-степе при каждом
  изменении `common`.
- **Не позволяйте потребляющей секции `tasks.md` (frontend/backend)
  начинаться раньше, чем секция `## Common` попала в репозиторий и
  опубликована.** Этот шлюз существует, чтобы вы никогда не собирали код
  против API, который ещё меняется.
- **Не двигайте указатель сабмодуля `specifications` в этом
  workflow-репозитории просто так** — эта фиксация (pin) — забота
  release/gitops-инструментов, отдельная от обновления версии пакета в
  вашем собственном репозитории.

## Диагностика

- `openspec doctor` — проверяет корректность настройки OpenSpec
  root/store.
- Store не найден / команды не резолвятся в `specifications`: повторите
  шаг единоразовой регистрации выше — он привязан к машине и не
  отслеживается в git, поэтому на новом ноутбуке или после свежего клона
  его нужно выполнить снова.
