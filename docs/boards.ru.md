# Доски Jira

[🇬🇧 English](./boards.md) | 🇷🇺 Русский

**Короткий ответ: две доски на команду, разделённые по _треку_ — не одна доска и
не доска на роль.**

```
Team <name> — Discovery   Kanban, с лимитами WIP, Story    аналитик + тимлид
Team <name> — Delivery    Scrum, спринты, Task             разработчики + тестировщик
```

Это разделение не вопрос вкуса. Его вынуждает шлюз очерёдности: **до влития
интента не должно существовать ни одной ветки.** Одна доска этого обеспечить не
может: история, попавшая в спринт и взятая в работу сразу, не оставляет места на
написание и утверждение интента. Поэтому дискавери идёт **на спринт впереди**
доставки, а трек, идущий впереди другого, нуждается в собственной доске.

## Почему не доска на роль

Соблазнительно и неверно, по четырём причинам.

- **Работа течёт через роли, а не принадлежит им.** Одна история проходит
  аналитика → тимлида → тестировщика и разработчиков. Разложенная на четыре
  доски, она нигде не видна целиком, и каждая передача становится невидимой ровно
  тогда, когда её и надо видеть.
- **Роль — это фильтр, а не доска.** «Моя работа» — это
  `assignee = currentUser()`. Быстрый фильтр или дорожка; вы получаете это
  бесплатно, не разрывая поток.
- **Доски по ролям порождают бэклоги по ролям, а за ними локальную
  оптимизацию.** Аналитик «заканчивает» десять интентов, пока разработчики
  захлёбываются; каждая доска выглядит здоровой, а система — нет.
- **Узкое место исчезает.** Смысл доски — показать, где копится работа. Доски по
  ролям гарантируют, что каждая очередь выглядит короткой.

## Почему не одна доска на всё

Тоже неверно, по причине, специфичной для этого процесса: дискавери и доставка —
действительно разная работа.

| | Дискавери | Доставка |
|---|---|---|
| единица | Story (= один мастер-интент) | Task (= один репозиторий, ветка, PR) |
| длительность | день-два | большая часть спринта |
| «готово» значит | интент влит | change заархивирован, сценарии проверены |
| ритм | нерегулярное поступление, поток | планируемый, по спринтам |

Сведение обоих на одну доску даёт набор колонок, бессмысленный для обоих, а
элементы дискавери забивают доску доставки на спринт вперёд, пока их никто не
трогает.

Есть и аргумент от иерархии. У вас уже есть:

```
1 Story = 1 мастер-интент                 ← доска Discovery
1 Task  = 1 репозиторий = 1 ветка = 1 PR  ← доска Delivery
```

Доски выпадают прямо из модели. Ничего выдумывать не нужно.

## `Team <name> — Discovery`

**Тип доски: Kanban.** Интенты поступают нерегулярно и не укладываются в
спринтовые коробки — им подходит поток, а не спринты.

**Фильтр**

```sql
project = PROJ AND issuetype = Story
  AND status IN ("To Do", "In Analysis", "In Review", "Ready for Dev")
  ORDER BY Rank ASC
```

Условие по статусам важно: как только история переходит в `In Progress`
(поднявшись от своих задач), она автоматически покидает эту доску и живёт на
Delivery. Никаких ручных переносов и историй, висящих на двух досках сразу.

**Колонки** — статусы истории из
[Jira ↔ SDD](./jira-sdd-mapping.ru.md), без изменений:

| Колонка | Значит | Лимит WIP | Кто |
|---|---|---|---|
| To Do | размер определён, метка `SDD`, id интента зарезервирован | — | тимлид |
| In Analysis | `/opsx:explore`, затем `/sdd:intent` | **3** | аналитик |
| In Review | `/sdd:review`; тестировщик укрепляет сценарии | **2** | тимлид + тестировщик |
| Ready for Dev | **интент влит** — ветки можно создавать | ≈ один спринт | — |

**Лимиты WIP — это и есть смысл доски.** Дискавери должен идти на спринт впереди
доставки и *не дальше*. Уйдёте дальше — интенты протухнут: общая база сместится
под ними, и анализ придётся переделывать. Важнее всего лимит на `Ready for Dev`:
когда он заполнен, аналитик перестаёт писать интенты и помогает в другом месте.

`Ready for Dev` — колонка «готово» этой доски и шлюз очерёдности. Попадание
истории туда и делает её задачи пригодными для следующего спринта.

## `Team <name> — Delivery`

**Тип доски: Scrum.** Реализация планируется и укладывается в спринты.

**Фильтр**

```sql
project = PROJ AND (
  (issuetype = Task AND parent IN (project = PROJ AND issuetype = Story))
  OR (issuetype IN (Bug, Chore) AND sprint IS NOT EMPTY)
)
ORDER BY Rank ASC
```

Задачи под историями **плюс** отдельные баги и рутина — которые согласно
[типам работ](./work-types.ru.md) минуют дискавери и попадают сюда напрямую. Это
и есть проверка того, что модель из двух досок обслуживает все дорожки, а не
только фичи.

**Колонки**

| Колонка | Значит | Кто |
|---|---|---|
| To Do | задача нарезана, ветка не начата | — |
| In Progress | `/opsx:propose` → `/opsx:apply` | разработчик |
| In Review | pull request открыт в Bitbucket | ревьюер |
| In Testing | развёрнуто в dev, сценарии прогоняются | тестировщик |
| Done | проверено, производный change заархивирован (`/opsx:archive`) | разработчик |

**Дорожки (swimlanes): по родительской истории.** Это самая ценная настройка на
обеих досках. Она делает разветвление видимым:

```
▾ PROJ-123  Вход через SSO
    backend  PROJ-124  ██ Done
    frontend PROJ-125  ██ In Progress      ← история не завершена
▾ PROJ-140  Экспорт в CSV
    backend  PROJ-141  ██ In Review
```

История завершена, когда завершена вся её дорожка. Без дорожек вы видите
двенадцать несвязанных задач и не можете понять, какой истории до выхода
осталась одна задача.

Учтите: это *Jira*-вид разветвления. Авторитетный — `make status`, который читает
репозитории, а не карточки: задачу можно пометить Done, пока её OpenSpec-change
не заархивирован, и поймает это только скрипт.

## Роли — это быстрые фильтры, а не доски

Добавьте на обе доски:

| Быстрый фильтр | JQL |
|---|---|
| Моя работа | `assignee = currentUser()` |
| Без исполнителя | `assignee IS EMPTY` |
| Заблокировано | `status = Blocked OR labels = blocked` |
| Backend / Frontend / GitOps | `component = <name>` |
| Пропущенные баги | `labels = escaped` |

Это закрывает любую потребность в «доске на роль», ничего не разрывая.
Разработчик открывает Delivery и жмёт *Моя работа*; аналитик открывает Discovery.

## Тестировщик присутствует на обеих досках

Единственная роль, намеренно живущая на обеих:

- **Discovery, `In Review`** — укрепление сценариев до влития интента
  (`/sdd:review`, `/sdd:tests`). Дешёвые правки.
- **Delivery, `In Testing`** — проверка сценариев на развёрнутом окружении.

Если ваш тестировщик появляется только на второй, процесс тихо вернулся к
тестированию в конце, и `/sdd:tests` не используется.

## Куда входит каждый тип работы

| Работа | Входит в | Минует дискавери? |
|---|---|---|
| Фича, улучшение, эксперимент | Discovery `To Do` | нет |
| Баг (спецификация верна) | Delivery `To Do` | да |
| Хотфикс | сразу Delivery `In Progress` | да — ретро-spec следом |
| Техдолг, рутина, подъём зависимости | Delivery `To Do` | да |
| Спайк | Discovery `In Analysis`, результат питает интент | н/д — кода не даёт |
| Инфраструктура | Delivery `To Do` (задача GitOps) | обычно да |

Полные правила в [типах работ](./work-types.ru.md).

## Ритм спринтов

```
Спринт N        Discovery: пишутся интенты для N+1
                Delivery:  реализуются интенты, влитые в N-1

Планирование спринта берёт только истории, уже находящиеся в Ready for Dev.
```

В этом весь фокус. К моменту, когда разработчик берёт задачу, её интент влит уже
неделю — значит, шлюз очерёдности выполнен без чьего-либо ожидания, и `make
check` проходит, потому что спецификация действительно вела код.

Если планирование хоть раз берёт историю *не* из `Ready for Dev` — остановитесь.
Это момент, когда метрика ломается, и починить его потом нельзя.

## Несколько команд

Дайте каждой команде свою **пару**. Историей владеет доска Discovery одной
команды — той, что владеет capability, а не репозиторием.

Когда задачи интента расходятся по командам, они попадают на доски Delivery
каждой команды, а история остаётся на доске Discovery команды-владельца.
Межкомандный вид — это вообще не доска Jira, а
`scripts/intent-status.sh <intent-id>`, который читает все репозитории
независимо от того, кто ими владеет. Не заводите третью доску — она разойдётся с
реальностью.

## Связь с дашбордами

Доски нужны, чтобы двигать работу; [дашборды](./dashboards.ru.md) — чтобы
замечать закономерности.

`Team <name> — Delivery` существует **и** как доска, **и** как ежедневный
дашборд, и имя у них общее намеренно: одна область, два вида. Доска показывает,
что двигать сегодня; дашборд — что стоит уже три дня.

У Discovery дашборда нет. Kanban-доска с лимитами WIP *уже является* своим
дашбордом: колонка упёрлась в лимит — это и есть весь сигнал.

## Чек-лист настройки

1. **Одна схема workflow на оба типа задач.** История использует все семь
   статусов; задача — пять и просто никогда не попадает в `In Analysis` и
   `Ready for Dev`. Две схемы — лишнее администрирование.
2. Создайте доску Discovery (Kanban) с фильтром по статусам, приведённым выше.
3. Проставьте лимиты WIP. Доска без них не удержит дискавери на одном спринте
   впереди, а это единственная причина её существования.
4. Создайте доску Delivery (Scrum), **дорожки по родительской истории**.
5. Добавьте быстрые фильтры на обе.
6. Ограничьте переход в `Ready for Dev` тимлидом — это шлюз очерёдности, и он
   должен быть осознанным действием.

## Типичные ошибки

| Ошибка | Последствие |
|---|---|
| доска на роль | поток не виден, бэклоги по ролям, узкое место скрыто |
| одна доска на оба трека | бессмысленные колонки; дискавери забивает доставку |
| нет лимита WIP на дискавери | интенты, написанные месяцами раньше, протухают |
| нет дорожек на доставке | не видно, какой истории до выхода осталась одна задача |
| взять историю не из `Ready for Dev` | ломает шлюз очерёдности, неисправимо |
| верить `Done` на Delivery как истине | карточка может быть Done с незаархивированным change — нужен `make status` |
| третья, межкомандная доска | немедленно расходится с реальностью; настоящий вид — `intent-status.sh` |
