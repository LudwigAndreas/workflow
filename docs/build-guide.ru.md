# Руководство по сборке

[🇬🇧 English](./build-guide.md) | 🇷🇺 Русский

Как построить этот процесс с нуля в порядке, при котором команда всё время
продолжает работать. Девять фаз, примерно **две недели настройки плюс один
спринт внедрения**.

## Прежде чем начать

**Два правила про порядок, оба выучены дорого.**

**Стройте петлю обратной связи раньше церемоний.** Фазы 1–7 — это сантехника:
ничьи ежедневные привычки не меняются, а в конце доска двигается сама. И только
потом (фаза 8) вы меняете то, как люди работают. Команды, вводящие процесс
раньше автоматизации, три месяца делают руками то, что должен делать скрипт,
решают, что процесс тяжёлый, и бросают его. Это самый частый способ провалить
затею.

**Пилотируйте на одном сервисе и одной команде.** Не на самом критичном и не на
самом неважном — возьмите сервис с реальным трафиком и команду, которая скажет
вам, когда неудобно. Раскатывайте на остальных после того, как пилот отработал
целый спринт от начала до конца.

| Фаза | Что получаете | Трудозатраты | Блокирующая? |
|---|---|---|---|
| [0](#фаза-0--решить) | решения записаны | 2 ч | да |
| [1](#фаза-1--репозитории-и-спецификации) | спецификации живут рядом с кодом | 1 д | да |
| [2](#фаза-2--jira) | типы задач, поля, статусы, доски | 1 д | да |
| [3](#фаза-3--гигиена-pr) | conventional PR, проверка SDD в CI | 4 ч | да |
| [4](#фаза-4--релиз-на-влитии) | версии, теги, образы без участия человека | 1 д | да |
| [5](#фаза-5--gitops-и-окружение-dev) | влитие → работает в dev за 15 минут | 2 д | да |
| [6](#фаза-6--обратная-связь-в-jira) | Fix Version, комментарии о выкатке | 4 ч | нет |
| [7](#фаза-7--промоушен-и-откат) | staging, подтверждение прода, откат | 1 д | нет |
| [8](#фаза-8--scrum-слой) | двухтрековые спринты, шлюзы | 1 спринт | нет |
| [9](#фаза-9--метрики) | DORA + соблюдение SDD | 4 ч | нет |

Фазы 6–9 помечены неблокирующими, потому что пайплайн работает и без них — но
именно на 6-й процесс становится видимым людям, никогда не открывающим GitHub,
а это и есть большая часть ценности, так что не останавливайтесь на 5-й.

## Фаза 0 — решить

Два часа в комнате с тимлидом, техлидом и одним разработчиком. Ответы
записываются в этот репозиторий; каждая следующая фаза их читает.

| Решение | Наш вариант по умолчанию | Почему |
|---|---|---|
| Ключ проекта Jira | один на продукт, например `PROJ` | одна доска, межрепозиторные story остаются читаемыми |
| Сервисы | по одному на деплой-единицу: `backend` `frontend` `common` `nginx` | линия версий у каждого своя |
| Окружения | `dev` `staging` `prod` | меньше — нечего промоутить; больше — никто не поддержит |
| Ветвление | trunk-based, только `main` | [релиз на влитии](./release.ru.md#принципы) требует этого |
| Стратегия влития | **только squash** | один коммит, одна запись changelog, надёжное извлечение ключей |
| Версионирование | semver на сервис из conventional commits | никаких файлов с версией, правленных руками |
| Длина спринта | 2 недели | один груминг, одно планирование, одно демо |
| Деление ёмкости | 60 фичи / 20 долг / 20 прерывания | [почему](./scrum.ru.md#ёмкость-и-правило-20) |
| Хранилище спецификаций | по репозиториям плюс маленькое общее | [почему](../AGENTS.md#source-of-truth) |
| Кто держит какую роль | имена, а не должности | шлюз без имени — шлюз, который никто не проходит |

**Готово, когда:** у каждой строки есть ответ и имя, закоммиченные в этот
репозиторий. Не «мы договорились» — записано. Половину из этого будут
переспрашивать на второй месяц, и записанный ответ прекратит спор за минуту.

## Фаза 1 — репозитории и спецификации

**Цель:** каждый репозиторий владеет своими спецификациями; маленькое общее
хранилище держит межрепозиторные контракты.

1. Создайте общее хранилище и зарегистрируйте его один раз на машину:

   ```bash
   gh repo create your-org/specifications --private
   git clone git@github.com:your-org/specifications.git ~/dev/specifications
   cd ~/dev/specifications && openspec init
   openspec store register ~/dev/specifications --id specifications
   openspec store list --json     # проверка
   ```

2. В **каждом** репозитории приложения:

   ```bash
   cd <app-repo>
   openspec init
   ```

   Затем скопируйте блоки `references:` и `rules:` из
   [`src/backend/openspec/config.yaml`](../src/backend/openspec/config.yaml) в
   его `openspec/config.yaml`. Блоки `rules:` — это то, что не даёт агенту
   генерировать `design.md` и `tasks.md` в бизнес-proposal, см.
   [propose vs. plan](../AGENTS.md#propose-vs-plan-who-writes-what).

3. Подключите сабмодули этого репозитория, чтобы авторы proposal получали
   межрепозиторный контекст:

   ```bash
   scripts/add-repo.sh backend git@github.com:your-org/backend.git
   scripts/add-repo.sh frontend git@github.com:your-org/frontend.git
   make init && make doctor
   ```

4. **Засейте основные спецификации.** Не пытайтесь описать существующую
   систему. Пишите спецификации только на те возможности, которые меняете:
   первая story, трогающая чекаут, пишет спецификацию чекаута. Проект
   «опишем всё» рождает документ, который никто не читает и который через
   месяц неверен.

**Готово, когда:** `openspec list` работает изнутри репозитория приложения без
флагов, а `openspec list --store specifications` — откуда угодно.

**Пропустите — и:** спецификации централизуются, за недели расходятся с кодом,
и вся модель схлопывается в вики.

## Фаза 2 — Jira

**Цель:** доска способна представить пайплайн.

1. **Типы задач:** Epic, Story, Task, Bug, Spike, Incident. Больше ничего.
2. **Кастомные поля** — [ровно четыре](./automation.ru.md#кастомные-поля-jira-которые-нужно-создать):
   `Change ID`, `Deployed Environments`, `Severity`, `Timebox`.
3. **Метки:** `SDD` (метрика), `feature-flag`, `tech-debt`.
4. **Статусы** в порядке workflow:
   `Intake → Specifying → Scenario review → Spec approval → Ready → In progress
   → In review → Deployed to dev → Verifying → Ready to release → Done`.
5. **Две доски** над одним проектом, см.
   [Scrum-слой](./scrum.ru.md#две-доски):
   - *Discovery*, фильтр `status in (Intake, Specifying, "Scenario review",
     "Spec approval", Ready)`.
   - *Delivery*, фильтр `status in (Ready, "In progress", ...)`, дорожки по
     Epic'ам.
6. **Свяжите Jira с GitHub** — официальным приложением GitHub for Jira. Именно
   оно вообще позволяет событиям веток и PR двигать карточки.
7. **Заведите бот-аккаунт** и его API-токен. Права: переводить задачи,
   редактировать задачи, добавлять комментарии, управлять версиями. Больше
   ничего.

**Готово, когда:** пуш ветки `PROJ-1-test` сам переводит `PROJ-1` в
`In progress`.

**Пропустите — и:** всё нижележащее продолжит работать, но статус будут вести
руками, к четвергу он будет неверен, и доске перестанут верить.

## Фаза 3 — гигиена PR

**Цель:** входы, которые читает релизный пайплайн, гарантированно
правильной формы.

1. Настройки репозитория → **разрешить только squash-влитие**. Отключите
   merge-коммиты и rebase. Это не вопрос стиля: с merge-коммитами сканирование
   диапазона тегов подхватывает промежуточные сообщения, и Fix Version попадают
   не на те задачи.
2. Установите шаблон сообщения squash-коммита в **«Pull request title and
   description»**.
3. Скопируйте два проверочных workflow:

   ```bash
   cp .github/workflows/pr-conventions.yml <app-repo>/.github/workflows/
   cp .github/workflows/sdd-check.yml      <app-repo>/.github/workflows/
   ```

4. Branch protection на `main`: обе проверки обязательны, одно подтверждающее
   ревью, прямые пуши запрещены — **включая админов**. Обход админом
   используется ровно один раз, а потом навсегда.

**Готово, когда:** PR с заголовком `wip` падает, а PR с заголовком
`feat(auth): add SSO callback` в ветке `PROJ-2-sso` проходит, и ключ
автоматически дописан в его тело.

**Пропустите — и:** фаза 4 выдаст неверные версии и неверные Fix Version, и вы
не заметите этого неделями.

## Фаза 4 — релиз на влитии

**Цель:** каждое влитие в `main` даёт версию, тег и образ без участия человека.

1. Скопируйте релизный workflow и задайте имя сервиса:

   ```bash
   cp .github/workflows/release.yml <app-repo>/.github/workflows/
   sed -i '' 's/SERVICE: backend/SERVICE: <your-service>/' \
     <app-repo>/.github/workflows/release.yml
   ```

2. Задайте переменные и секреты из
   [инвентаря конфигурации](./automation.ru.md#инвентарь-конфигурации).
3. **Поставьте первый тег руками**, чтобы у вычисления версии была база:

   ```bash
   git tag -a backend-1.0.0 -m "baseline before automated releases"
   git push origin backend-1.0.0
   ```

4. Прогоните вхолостую до включения:

   ```bash
   scripts/release-version.sh --service backend
   scripts/release-version.sh --service backend --notes
   scripts/jira-release.sh --service backend --version 1.0.1 --dry-run
   ```

**Готово, когда:** влитие PR с заголовком `fix(x): y` даёт тег `backend-1.0.1`,
GitHub release с notes и образ, запушенный по digest, — и вы нигде не набирали
`1.0.1`.

## Фаза 5 — GitOps и окружение dev

**Цель:** от влития до работы в `dev` меньше пятнадцати минут, и никто не
запускает команду выкатки.

1. Структура каждого GitOps-репозитория:

   ```
   gitops_backend/
     apps/backend/
       base/
       overlays/{dev,staging,prod}/kustomization.yaml
   ```

   Каждый оверлей пинит образ по **digest**, а не по тегу —
   [почему](./release.ru.md#теги-и-образы).

2. Создайте по одному приложению Argo CD на сервис на окружение с именем
   `<service>-<env>` (`deploy.yml` опрашивает именно это имя). Auto-sync
   **включён** для `dev` и `staging`, **выключен** для `prod` — прод
   синхронизируется при влитии своего PR.

3. Скопируйте workflow выкатки и задайте его переменные:

   ```bash
   cp .github/workflows/deploy.yml <gitops-repo>/.github/workflows/
   ```

4. Защитите продовый оверлей:
   [`CODEOWNERS` + branch protection](./automation.ru.md#защита-продового-оверлея)
   на `apps/*/overlays/prod/**`. `dev` и `staging` защищать не нужно — они
   должны двигаться постоянно.

5. Определите health честно. Readiness-проба, отдающая 200, — это не здоровье:
   Argo должен видеть, что ворклоад реально обслуживает. Плохие определения
   здоровья делают автоматический откат либо бесполезным, либо страшным.

**Готово, когда:** влитие в `main` приводит к тому, что новый digest работает в
`dev`, без действий человека, меньше чем за пятнадцать минут.

**Пропустите — и:** промоутить нечего и события выкатки нет, так что у фаз 6 и
7 не будет триггера.

## Фаза 6 — обратная связь в Jira

**Цель:** любой может открыть тикет и увидеть, где работа, не спрашивая
разработчика. Эту фазу люди замечают.

1. Создайте поле `Deployed Environments`, если ещё нет, и запишите его
   `customfield_`-id:

   ```bash
   curl -sS -u "$JIRA_EMAIL:$JIRA_TOKEN" \
     "$JIRA_URL/rest/api/2/field" | jq -r '.[] | select(.name=="Deployed Environments") | .id'
   ```

2. Задайте `JIRA_FIELD_DEPLOYED_ENVS` в GitOps-репозиториях.
3. Проверьте на одной реальной задаче до того, как довериться:

   ```bash
   scripts/jira-deploy.sh --service backend --version 1.0.1 \
     --env dev --keys "PROJ-1" --dry-run
   ```

4. Добавьте [правила автоматизации Jira](./automation.ru.md#правила-автоматизации-jira)
   1–7 — сначала движение по доске. Правила 8–14 добавьте неделей позже, когда
   1–7 начнут вызывать доверие.
5. Проверьте **идемпотентность**: прогоните ту же выкатку дважды и убедитесь,
   что у задачи один комментарий, а не два.

**Готово, когда:** влитый PR без чьего-либо участия приводит к тому, что в
тикете появляется `🚀 Выкачено в dev — backend 1.0.1`, поле показывает `dev`, а
карточка стоит в `Deployed to dev`.

## Фаза 7 — промоушен и откат

**Цель:** проверенная работа доезжает до прода по решению, а не по скрипту
выкатки; а отменить это скучно.

1. Добавьте правило автоматизации Jira 6 — «Send web request», которое шлёт
   `repository_dispatch` типа `verified`, когда тестировщик переводит story в
   `Ready to release`. Токен GitHub положите в секреты автоматизации Jira.
2. Проверьте промоушен в staging, передвинув одну реальную story.
3. Сделайте **холостой прогон промоушена в прод** с пустым изменением, целиком,
   включая подтверждение. Сделайте это до того, как понадобится.
4. **Отрепетируйте откат намеренно**, в рабочее время, при всей команде:

   ```bash
   scripts/promote.sh --service backend --to prod --digest <previous> --version <previous> --pr
   ```

   Путь отката, который ни разу не проходили, не существует. После этого
   репетируйте раз в квартал.

5. Запишите, кто утверждает прод и кто его подменяет. Единственный утверждающий
   в отпуске — это незапланированная заморозка релизов.

**Готово, когда:** перенос тестировщиком одной карточки приводит к выкатке в
staging, одно подтверждение — к выкатке в прод, и вы уже один раз откатывались
специально.

## Фаза 8 — Scrum-слой

**Цель:** процесс, которому следуют люди, совпадает с пайплайном, который
крутят машины.

Только теперь, когда доска двигается сама, меняйте то, как работает команда.

**Спринт 1 — запустить оба трека, намеренно плохо.**
- Возьмите **три** story на трек discovery. Только три; первые proposal
  занимают вдвое больше времени, чем будут через месяц.
- Доставьте то, что уже в работе, как бы оно ни было описано. Не натягивайте
  шлюзы на уже написанный код — метрика в этом спринте будет низкой, и это
  правильное показание.
- Проведите [груминг](./scrum.ru.md#груминг) по-настоящему, с правилом размера
  на столе.

**Спринт 2 — пул Ready существует.**
- Доставьте три story, описанные в спринте 1. Это первый спринт, где шлюз 4
  ничего не стоит, и команда это чувствует.
- Опишите пять-шесть для спринта 3.
- Соблюдайте DoR: в delivery не входит ничего, что не пришло из пула.

**Спринт 3 — устойчивый режим.**
- В пуле ~1,5 спринта работы.
- Применяйте деление 60/20/20 по-настоящему, включая пустую долю прерываний.
- Начинайте читать метрику SDD как число, которое что-то значит.

**Готово, когда:** завершился спринт, в котором ни одна ветка не была срезана
до влития своей спецификации, и никому не пришлось об этом напоминать.

**Режим отказа, за которым следить:** пул Ready опустевает в спринте 3, потому
что discovery задавили давлением доставки. Если это случилось — работа
discovery была невидимой: вынесите её на доску с собственными оценками.

## Фаза 9 — метрики

**Цель:** понимать, работает ли всё это.

Постройте один дашборд. Не пять.

| Метрика | Источник | Здоровое значение |
|---|---|---|
| Частота выкаток | тегов на сервис в неделю | ежедневно и чаще |
| Lead time изменения | влитие на шлюзе 4 → выкатка в прод | < 5 дней |
| Доля неудачных изменений | откаты + хотфиксы ÷ промоушены | < 15% |
| Время восстановления | открытие аварии → выкатка в прод | < 1 ч |
| Соблюдение SDD | прошедшие `make check` ÷ закрытые story | > 90% |
| Глубина пула Ready | количество в `Ready` ÷ velocity | 1–2 спринта |
| Трата прерываний | незапланированные очки ÷ ёмкость | < 20% |

```bash
make check                              # локально
make check-shared                       # общее хранилище
JIRA_URL=… JIRA_TOKEN=… make check      # плюс проверка метки
```

**Показывайте метрики команде и никогда не отправляйте наверх как оценку.** Как
только соблюдение SDD станет числом, по которому кого-то судят, story получат
метку без дисциплины, и вы уничтожите единственный прибор, который говорил вам,
работает ли процесс.

**Готово, когда:** ретро начинается с дашборда на экране, и никто к нему
специально не готовился.

## Минимум на два дня

Если двух недель нет, вот подмножество с лучшим отношением пользы к затратам.
Оно полезно и само по себе.

1. **Фаза 3** — только squash, conventional-заголовки, имена веток. *4 ч.*
2. **Фаза 4** — релиз на влитии. *1 д.*
3. **Фаза 6, только слой 1** — Fix Version проставляется на теге. *2 ч.*

Вы получаете: автоматические версии, автоматические теги и release notes и
каждую задачу Jira с указанием, в какой сборке она уехала. Одно это убивает
вопрос «когда уедет моя правка?», который обычно и есть самая громкая боль.
Остальное добавьте позже, по порядку.
