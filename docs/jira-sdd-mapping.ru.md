# Соответствие Jira ↔ SDD

[🇬🇧 English](./jira-sdd-mapping.md) | 🇷🇺 Русский

Как соотносятся задачи Jira, OpenSpec-change, ветки и корпоративная метрика
SDD. Это не бюрократия: метрику измеряют, и именно это соответствие делает её
измеримой без параллельной системы учёта.

## Модель

```
1 Epic  = N Story                        фича, слишком большая для одного интента
1 Story = 1 мастер-интент                ← здесь живёт метка SDD
1 Task  = 1 репозиторий = 1 change       ← одна ветка, один pull request
        = 1 секция handoff
```

**Task режут выкладку, а не интент.** Task истории — это её срезы по
репозиториям. Лекарство от слишком большой истории — **Epic**, а не больше
Task.

## Метрика «история следовала SDD»

История засчитывается, когда:

1. на ней стоит метка **`SDD`**, и
2. существует **ветка, названная по ключу истории** — это выполняется либо
   самой историей, либо вложенной в неё задачей, так что ветка дочерней Task
   засчитывается

Это определение компании. Чтобы выполнить его *механически*, нужно чуть больше,
и `scripts/check-sdd.sh` проверяет всё перечисленное:

| Проверка | Зачем |
|---|---|
| интент содержит `jira: PROJ-123` | связывает интент с помеченной историей |
| change репозитория содержит `intent:` и `intent_store:` | связывает код с интентом |
| change репозитория содержит `jira: PROJ-124` | связывает код с задачей |
| проходит `openspec validate` | спецификация корректна, а не просто существует |
| ветка соответствует шаблону имени | Jira может сопоставить ветку с задачей |
| **интент влит раньше первого коммита** | спецификация вела код, а не наоборот |

Последний пункт и отличает *следование SDD* от *метки SDD*, и его **нельзя
исправить задним числом**. Если ветку создали до влития интента, честный ответ
— эта история не следовала SDD. Переписывание истории ради прохождения проверки
уничтожает смысл измерения.

```bash
make check                              # всё в этом checkout
JIRA_URL=... JIRA_TOKEN=... make check  # плюс проверка метки SDD через Jira
```

Без `JIRA_URL`/`JIRA_TOKEN` проверки метки **пропускаются, а не считаются
пройденными** — скрипт прямо об этом сообщает.

## Имена веток

```
<STORY-KEY>/<TASK-KEY>-<slug>      PROJ-123/PROJ-124-sso-token-endpoint
<STORY-KEY>-<slug>                 PROJ-123-sso-login      (история в одном репозитории)
```

Первая форма разрешается и в помеченную **историю**, и в **задачу** — именно
поэтому ветка дочерней Task засчитывается истории. Используйте её всегда, когда
ветки принадлежат задачам, а это обычный случай: большинство историй затрагивает
больше одного репозитория.

## Размер: story, task или epic?

Вопрос, который всё решает:

> Можно ли `proposal.md` + `specs/` для этого проверить и утвердить как **одно
> решение**, и описывает ли это **одно** изменение пользовательской capability?

| Ответ | Единица |
|---|---|
| Да | **одна Story** = один мастер-интент |
| Да, но ложится в несколько репозиториев | всё равно **одна Story**; каждый репозиторий — **Task** |
| Нет — несколько независимых изменений capability | **Epic** из нескольких Story |

**Репозитории — не причина делить историю.** Один интент, охватывающий backend
и frontend, — норма; ровно для этого и нужен `handoff.md`. Разделив «пользователь
входит через SSO» на историю backend и историю frontend, вы теряете принятое
решение и получаете две спецификации, которые надо держать в согласии.

Признаки, что нужен был Epic:

- specs описывают две capability, которые могут выйти независимо
- ревьюеры раз за разом одобряют одну половину и возражают против другой
- в порядке раскатки больше трёх упорядоченных этапов
- в `handoff.md` пять и более секций репозиториев

Признаки, что разделили слишком мелко:

- дельта spec истории — один сценарий
- specs двух историй имеют смысл только вместе
- одну историю нельзя проверить, пока не развёрнута другая

## Жизненный цикл задачи и кто двигает карточку

| Статус Jira | Значит | Двигает |
|---|---|---|
| To Do | интент не написан | — |
| In Analysis | интент пишется | аналитик |
| In Review | интент на утверждении | тимлид |
| Ready for Dev | интент влит; можно создавать ветки | тимлид, при влитии |
| In Progress | хотя бы одна задача в работе | разработчики |
| In Testing | развёрнуто; сценарии проверяются | тестировщик |
| Done | все задачи закрыты, интент архивирован | тот, кто архивирует |

Эти статусы и есть колонки двух командных досок: истории идут по доске
Discovery, задачи — по доске Delivery. См. [доски](./boards.ru.md).

История не может попасть в **Ready for Dev** до влития её интента. Этот переход
*и есть* шлюз очерёдности — его соблюдение в Jira и делает метрику честной,
потому что это момент, когда разработчикам разрешено начинать.

## Поля, которые стоит заполнять

| Поле | Значение | Зачем |
|---|---|---|
| Label | `SDD` | метрика читает его |
| Story: кастомное поле `Intent ID` | kebab-case id интента | связывает Jira с интентом |
| Task: parent | история | ветка разрешается вверх к помеченной истории |
| Fix Version | `<service> <semver>` | связывает релиз с историей |

Если кастомного поля нет, положите id интента в описание истории отдельной
строкой `intent: <intent-id>` — `check-sdd.sh` не читает для этого Jira, но
люди и ревьюеры читают.

## Типичные сбои

| Симптом | Причина | Что делать |
|---|---|---|
| метрика падает, хотя всё выглядит верно | нет `jira:` в `.openspec.yaml` | добавить |
| change репозитория не виден разветвлению | нет ключа `intent:` | добавить `intent:` и `intent_store:` |
| шлюз отказывает, хотя работа сделана | change не заархивирован в своём репозитории | выполнить там `/opsx:archive` |
| шлюз пишет «чек-лист лжёт» | галочку поставили руками | снять её; использовать `intent-gate.sh --tick` |
| падает проверка очерёдности | ветку создали до влития интента | не исправимо — сообщить честно |
