# Разработчик

[🇬🇧 English](./developer.md) | 🇷🇺 Русский

Для инженеров фронтенда, бэкенда, common, gitops и nginx. Вы работаете в
**режиме B**: склонирован ровно один репозиторий приложения, IDE и агент
запущены в нём. Вам **не нужен** этот репозиторий `workflow`, и не нужен ни один
чужой репозиторий на диске.

Сначала прочитайте [пайплайн](../pipeline.ru.md) и
[связку Jira ↔ SDD](../jira-sdd-mapping.ru.md). Вы владеете **шлюзами 5 и 6**.

## Чем вы владеете

`design.md` (**как**), `tasks.md` (пошаговый план) и код. `design.md` и
`tasks.md` вы пишете **всегда** — независимо от того, пришёл proposal от вас
(локальное изменение) или от аналитика (общий контракт).

## Разовая настройка машины

Клонируйте только свой репозиторий:

```bash
git clone ssh://git@bitbucket.acme.com/plat/<frontend|backend|...>.git
cd <your-repo>
```

Зарегистрируйте общее хранилище `specifications` один раз на машину — не на
репозиторий, и это не отслеживается git, поэтому на новом ноутбуке нужно
повторить:

```bash
git clone git@github.com:LudwigAndreas/specifications.git ~/dev/specifications
openspec store register ~/dev/specifications --id specifications
openspec store list --json      # проверка
```

Дальше обычные команды `openspec` работают с *вашим собственным*
`openspec/specs` + `openspec/changes`. Флаг `--store specifications` достаёт
общее хранилище изнутри вашего репозитория, ничего больше не выкачивая.

## Две формы работы

Определите форму **до** того, как трогать OpenSpec.

| | Затрагивает только ваш репозиторий | Затрагивает контракт, который потребляет другой репозиторий |
|---|---|---|
| Пример | внутренний рефакторинг, багфикс, локальная фича | новый/изменённый API между FE и BE, общее событие, всё что публикует `common` |
| Где proposal | ваш репозиторий, без `--store` | `specifications` — пишет аналитик, не вы |
| Кто пишет `proposal.md` + `specs/*.md` | вы | аналитик |
| Кто пишет `design.md` + `tasks.md` | **вы** | **вы** |

Если вашей story нужен контракт, которого никто ещё не предложил — не пишите
спецификацию контракта сами, обратитесь к аналитику. У него есть межрепозиторный
контекст, необходимый чтобы договориться корректно, а планирование под
несогласованный контракт означает переделку.

## Шлюз 5 — планирование

Дельта вашей story уже влита (шлюз 4). Теперь:

```bash
openspec instructions design --change <id> [--store specifications] --json
openspec instructions tasks  --change <id> [--store specifications] --json
```

Или просто запустите `/sdd:plan <change-id>` — он оборачивает оба и следит за
соглашением о секциях.

**`design.md`** — пишите, когда изменение сквозное, добавляет зависимость,
включает миграцию или имеет неочевидный подход. Пропустите для маленького
локального изменения; не создавайте ритуал на пустом месте.

**`tasks.md`** — одна нумерованная секция на затронутый репозиторий, каждая со
своим ключом задачи Jira:

```markdown
## 1. Common (PROJ-124)

- [ ] 1.1 Добавить тип SsoAssertion
- [ ] 1.2 Опубликовать пакет 2.4.0

## 2. Backend (PROJ-125)

<!-- шлюз: не начинать, пока 1.2 не опубликована -->
- [ ] 2.1 Поднять common до 2.4.0
- [ ] 2.2 Реализовать callback
```

Ключ Jira в заголовке — не украшение: `scripts/check-sdd.sh` его проверяет,
и именно он делает прогресс story в Jira и `openspec status` согласованными.

Запушьте коммит с планом и покажите техлиду до начала кодирования. Неверный
подход, пойманный здесь, стоит час; пойманный на ревью PR — спринт.

## Шлюз 6 — реализация

**Именование ветки** — это часть метрики, а не вопрос стиля:

```
story в одном репозитории (без task'ов):  PROJ-140-fix-session-expiry
story в нескольких (ваш task):            PROJ-123/PROJ-125-backend-sso-endpoint
```

Во второй форме — оба ключа, чтобы ветка связалась и со Story, и с вашим Task.

Далее:

- Если ваша задача зависит от контракта `common`, **дождитесь публикации** и
  только потом поднимайте зависимость. Не начинайте против неопубликованного
  кода — именно это означает комментарий-шлюз в `tasks.md`.
- Запустите `/opsx:apply`, чтобы пройти `tasks.md` сверху вниз с агентом. Он
  отмечает каждую задачу `[x]` по мере выполнения и останавливается на
  неоднозначностях. Не позволяйте ему угадывать за непонятным требованием —
  неоднозначная спецификация это провал шлюза 3, о котором стоит сообщить, а не
  импровизировать вокруг него.
- Ветка → PR **в свой репозиторий** → ревью → CI → **squash-влитие**.
  Заголовок PR — conventional commit (`feat(auth): add SSO callback`), потому
  что он становится единственным коммитом в `main`, и релизный пайплайн читает
  именно его.

Перед открытием PR запустите `make check`, чтобы убедиться, что метрика пройдёт.

## Передача на шлюз 9

Тестировщик прогоняет каждый сценарий из `specs/*.md` на **выкаченном
окружении `dev`**, а не на вашей ветке — и Jira сообщает ему о готовности сама,
без чьих-либо просьб. Если
сценарий невозможно исполнить — это настоящая находка: либо код не соответствует
спецификации, либо спецификация была неверна. И то и другое стоит узнать до
архивации.

## После влития — шлюзы 7–11

**Влитие вашего PR — ваше последнее действие по story.** Всё дальнейшее
автоматизировано, см. [release.ru.md](../release.ru.md).

| Шлюз | Что происходит | Вы |
|---|---|---|
| 7 | версия вычислена, тег и образ собраны, Fix Version проставлен | ничего |
| 8 | GitOps выкатывает `dev`, тикет комментирует себя сам | ничего |
| 9 | тестировщик проверяет на `dev` | отвечаете на вопросы |
| 10 | staging автоматически, прод — по подтверждению техлида | ничего |
| 11 | архивация | ниже |

Единственное, что это возлагает на вас: **тип коммита определяет версию.**
`fix:` — patch, `feat:` — minor, `feat!:` — major, на который обязаны
отреагировать все потребители. Исправить это потом негде — неверный тип
выпускает версию, которая врёт.

Когда изменение работает **в проде** во всех затронутых репозиториях:

```bash
/opsx:archive <change-id>                          # локальное изменение
/opsx:archive <change-id> --store specifications   # общий контракт
```

**Для изменения контракта дождитесь, пока в прод попадут все потребляющие
репозитории** — а не момента, когда влита ваша половина.

## Статус, не выходя из репозитория

```bash
openspec list   --store specifications
openspec show   <change-id> --store specifications
openspec status --change <change-id> --store specifications --json
```

## Команды

| Команда | Когда |
|---|---|
| `/opsx:explore` | продумать требования или подход до обязательств |
| `/sdd:intake` | начать локальное изменение (proposal + specs) |
| `/sdd:plan` | написать `design.md` + `tasks.md` с ключами Jira в секциях |
| `/opsx:apply` | пройти `tasks.md` от начала до конца, по одной задаче |
| `/sdd:gate` | проверить готовность к метрике перед открытием PR |
| `/opsx:archive` | закрыть выкаченное изменение |

## Чего делать нельзя

- **Не пишите `proposal.md`/`specs/*.md` для межрепозиторного контракта.**
  Подключите аналитика вместо того, чтобы угадывать контракт.
- **Не начинайте ветку до влития дельты.** Это провал метрики, и его нельзя
  исправить задним числом.
- **Не подключайте `common` сабмодулем во frontend или backend.** Зависьте от
  опубликованной версии пакета; сабмодуль связывает обе стороны в жёсткую сцепку.
- **Не начинайте потребляющую секцию до публикации `## Common`.**
- **Не двигайте указатель сабмодуля `specifications` в репозитории workflow без
  необходимости** — этот пин относится к релизной оснастке.

## Диагностика

- `openspec doctor` — проверка корня OpenSpec и хранилища.
- Хранилище не найдено: повторите разовую регистрацию. Она на машину и не
  хранится в git.
- `make check` падает на шаблоне ветки: переименуйте ветку, см.
  [связку Jira ↔ SDD](../jira-sdd-mapping.ru.md#именование-веток).
