# Тимлид

[🇬🇧 English](./team-lead.md) | 🇷🇺 Русский

Вы владеете **приёмом работ, определением размера и решением о влитии**. Ваше
одобрение — момент, когда несколько человек начинают строить параллельно по
одному документу.

## Ваш цикл

```
приём работ   направить работу на её дорожку, определить размер,
              поставить метку SDD, зарезервировать id интента,
              нарезать задачи по репозиториям
/sdd:review   проверить интент, одобрить или вернуть
влитие        → это шлюз очерёдности
/sdd:status   следить за разветвлением, разблокировать
```

## Приём работ

Для каждой новой позиции:

1. **Определите дорожку.** Какая из [типов работ](../work-types.ru.md)? Не
   всему нужен интент — багфиксу, рефакторингу или рутине не нужен, и прогон их
   через полный процесс — способ добиться того, чтобы процесс забросили.
2. **Определите размер.** Можно ли это проверить и утвердить как одно решение,
   описывающее одно изменение capability? Если нет — это Epic. Несколько
   репозиториев — *не* причина делить.
3. **Поставьте метку `SDD`**, если это история, идущая по процессу. Метрика
   читает эту метку.
4. **Зарезервируйте id интента** — kebab-case, от сути, а не от ключа Jira:
   `add-sso-login`, а не `proj-123`.
5. **Нарежьте задачи по репозиториям**, когда появится таблица затронутых
   репозиториев, по одной на репозиторий, каждая со своим ключом для ветки.

## Ревью

Это ключевой шлюз всего процесса. После вашего влития тестировщик и несколько
разработчиков строят по этому документу **не согласовывая ничего**. Размытый
контракт будет истолкован в каждом репозитории по-своему, и расхождение
всплывёт на интеграции, спустя дни.

`/sdd:review` проходит полный чек-лист. Пункты, которые ловят больше всего:

- **Покрытие.** Каждое требование в `specs/` принадлежит хотя бы одной секции
  репозиторию из таблицы «Репозитории» интента. Посчитайте объединение сами.
- **Точность контракта.** Мог бы разработчик строить по каждому обязательству
  *до появления второй стороны*? Если нет — возвращайте; это самое ценное, что
  вы проверяете.
- **Несчастливые пути.** У каждого требования есть хотя бы один.
- **Четыре решётки** у сценариев. Три разбираются как ничто, молча.
- **Требования MODIFIED** скопированы целиком, со сценариями. Сверьте сами с
  `openspec/specs/<capability>/spec.md`; частичная копия удалит сценарии при
  архивации.
- **Порядок раскатки** согласуется с `Depends on` каждого репозитория, и
  поставщики ложатся раньше потребителей.
- **Блокирующие неизвестности.** Открытый вопрос, способный изменить specs,
  блокирует влитие. «Разберёмся по ходу реализации» означает, что каждый
  репозиторий разберётся по-своему.

Запрашивайте изменения, не правьте интент сами. Им владеет аналитик, а молчаливая
правка никого ничему не учит.

## Шлюз очерёдности

**Ни в одном репозитории не должно существовать ветки до влития интента.**

Метрика фиксирует, легла ли спецификация раньше первого коммита, и это **не
исправить задним числом**. В Jira история не может попасть в *Ready for Dev* до
влития — этот переход и есть шлюз, потому что это момент, когда разработчикам
разрешено начинать.

Если ветка уже существует, скажите прямо: история не следовала SDD.
Переписывание истории ради прохождения проверки уничтожает смысл измерения.

## Наблюдение за разветвлением

```bash
make status                 # каждый интент, по данным самих репозиториев
make gate INTENT=<id>       # можно ли уже архивировать этот?
make check                  # метрика SDD
```

`intent-status.sh` читает репозитории, а не галочки, поэтому он вскрывает три
конкретные лжи: работа заархивирована, но галочка не стоит; галочка стоит, а
change ещё открыт; галочка стоит, а change вообще нет.

На что реагировать:

- репозиторий **не начал**, пока другие заканчивают — он станет критическим путём
- репозиторий **заблокирован** поставщиком, который не опубликовался
- **исправление контракта**, поднятое разработчиком — это срочно, потому что
  другая сторона прямо сейчас строит по старой версии

## Ваши две доски

`Team <name> — Discovery` (Kanban, Story) и `Team <name> — Delivery` (Scrum,
Task). Разделены по треку, а не по ролям: доска на роль скрывает узкое место и
порождает бэклоги по ролям.

Две настройки — ваши, и обе важнее, чем кажутся:

- **Лимиты WIP на Discovery.** Именно они удерживают дискавери на *одном*
  спринте впереди доставки. Уйдёте дальше — интенты протухнут, потому что общая
  база сместится под ними.
- **Переход в `Ready for Dev` — только ваш.** Это шлюз очерёдности.
  Планирование спринта может брать только истории, уже находящиеся там; возьмёте
  другую — метрика сломается неисправимо.

Полная настройка, фильтры и колонки: [доски](../boards.ru.md).

## Ваши два дашборда

Оба ваши, и они намеренно работают с разной периодичностью.

**`Team <name> — Delivery`**, ежедневно, на стендапе. Заблокированная работа,
зависшие статусы, влитые интенты, которые никто не начал. Всё на нём должно быть
отработано до обеда.

**`Team <name> — Quality`**, **ежемесячно**, вместе с тестировщиком.
Пропущенные дефекты, открытые баги по приоритету, средний возраст открытых
багов. Эти числа не могут осмысленно измениться за день — ежедневный просмотр
порождает реакцию на шум и приучает команду к тому, что дашборды нужны, чтобы
их игнорировать.

На месячном обзоре важен один вопрос, задаваемый по каждому пропущенному
дефекту: *какого сценария не хватало и не было ли его потому, что его не было в
интенте?* В этом процессе пропущенный дефект почти всегда восходит к
отсутствующему несчастливому сценарию в мастер-интенте, а значит, это дефект
`/sdd:review` — вашего, — а не тестирования.

Ни на одном из дашбордов нет ни метрики SDD, ни разветвления. И то, и другое
живёт вне Jira: `make check` читает git, `make status` читает репозитории.
Запускайте их рядом с доской.

Настройка, гаджеты и JQL: [дашборды](../dashboards.ru.md).

## Что не ваше

- сами требования — аналитик
- технический дизайн и разбивка задач — реализующий разработчик
- стратегия тестирования — тестировщик

Ваш рычаг — размер, ревью и поддержание разветвления разблокированным.

## Типичные ошибки

| Ошибка | Последствие |
|---|---|
| деление истории по репозиториям | две спецификации, которые надо держать в согласии; решение потеряно |
| одобрение размытого контракта | сбой интеграции спустя дни |
| ветка раньше влития | история не может засчитаться в метрику |
| правка интента самим на ревью | аналитик ничему не научился; теперь он ваш |
| прогон рутины через полный процесс | процесс забрасывают |
