# Аналитик / архитектор

[🇬🇧 English](./analytics.md) | 🇷🇺 Русский

Вы превращаете намерение story в согласованное, пригодное для ревью описание
поведения. Вы работаете в **режиме A** — этот репозиторий `workflow`, где все
репозитории приложения подключены сабмодулями рядом, чтобы изменение,
охватывающее несколько репозиториев, можно было оценить с полным контекстом. Вы
**никогда** не трогаете код в `src/*`.

Сначала прочитайте [пайплайн](../pipeline.ru.md) и
[связку Jira ↔ SDD](../jira-sdd-mapping.ru.md). Вы владеете **шлюзом 2** и обычно
ведёте **шлюз 11**.

## Чем вы владеете

`proposal.md` (**зачем**) и `specs/*.md` (**что** — наблюдаемое поведение,
требования, сценарии). Это весь ваш выход.

Вы **не** пишете `design.md` и `tasks.md`. Дело не в статусе: они требуют знания
паттернов и соглашений целевого кода, которого у вас перед глазами нет, поэтому
ваш черновик всё равно будет переписан реализующим разработчиком. Это ещё и
обеспечено механически: `openspec/config.yaml` объявляет `rules:` для обоих
артефактов, предписывающие любому агенту остановиться после `specs` при
черновике proposal.

## Настройка

```bash
git clone --recurse-submodules <this-repo-url> workflow
cd workflow
make init      # сабмодули + регистрация общего хранилища "specifications"
make doctor
make sync      # перед началом любой новой работы
```

## Что относится к `specifications`, а что нет

Общее хранилище содержит **только сквозные возможности**: контракты, о которых
должны договориться несколько репозиториев — API между фронтендом и бэкендом,
общие события, всё, что публикует `common`. Его намеренно держат маленьким.

Если story оказалась однорепозиторной — она **не ваша**. Передайте её
разработчику этого репозитория; он создаст proposal и реализует всё внутри
своего репозитория, а у вас в этом пути нет роли вообще.

## Шлюз 2 — написание proposal

**1. Возьмите story.** Она приходит от тимлида уже нарезанной, помеченной `SDD`
и с `change-id`. Если она не нарезана — если читается как несколько независимых
изменений возможностей — верните её, а не создавайте proposal, который никто не
сможет спланировать.

**2. Соберите затронутые репозитории в один вид**, вместо ручного жонглирования
каталогами:

```bash
openspec workset create <name>
openspec context --code-workspace ws.code-workspace
```

**3. Создайте изменение** с тем `change-id`, который зарезервировал тимлид:

```bash
openspec new change <change-id>                          # локальный репозиторий
openspec new change <change-id> --store specifications   # межрепозиторное
```

Запишите ключ story в `openspec/changes/<change-id>/.openspec.yaml`:

```yaml
schema: spec-driven
created: 2026-08-21
jira: PROJ-123
```

**4. Черновик.** Запустите `/sdd:intake` (или `/opsx:propose`) для нужного
корня. Он сгенерирует `proposal.md` и `specs/*.md`. **Остановитесь на этом** —
правила конфига остановят его до `design.md` и `tasks.md`.

**5. Пишите сценарии так, как их будет читать тестировщик**, потому что он
будет — на шлюзе 3. У каждого требования нужен хотя бы один `#### Scenario:` с
`WHEN`/`THEN`. Держите их наблюдаемыми — без имён классов, выбора библиотек и
шагов реализации.

**6. Откройте PR** в `specifications` (или в локальный репозиторий). Изменение
только с `proposal.md` + `specs/` проходит `openspec validate` и может быть
влито; `design`/`tasks` показываются как «blocked»/«ready», а не ошибки, так что
подделывать их ради влития не нужно.

## Передача на шлюз 3

Тестировщик ревьюит ваши сценарии до того, как техлид утвердит. Ожидайте, что
граничные случаи вернутся — это самый дешёвый момент, чтобы их найти: сценарий,
добавленный здесь, стоит минуты вместо переоткрытой story.

## Передача на шлюз 5

После влития сообщите разработчикам затронутых репозиториев, что изменение
готово к планированию. **Они** пишут `design.md` и `tasks.md`. Вы за ними не
бегаете; они сами найдут изменение:

```bash
openspec list --store specifications
openspec instructions design --change <id> --store specifications --json
```

## Отслеживание прогресса

```bash
openspec list   --store specifications
openspec show   <change-id> --store specifications
openspec status --change <change-id> --store specifications --json
```

`isComplete: false` **ожидаемо**, пока разработчик не добавит `tasks.md`. Это
значит «ещё не готово к реализации», а не «что-то сломано».

## Шлюз 11 — архивация

Когда **каждый** потребляющий репозиторий влил и выкатил свою часть:

```bash
/opsx:archive <change-id> --store specifications
```

Это переносит изменение в `changes/archive/` и синхронизирует
`specifications/openspec/specs/*` до новой канонической истины — той, на которой
будут строиться будущие proposal. Убедитесь, что выкатились все стороны, а не
только самая быстрая: ранняя архивация заставляет каноническую спецификацию
утверждать то, что ещё не везде правда.

## Команды

| Команда | Когда |
|---|---|
| `/opsx:explore` | продумать story до любых обязательств — ничего не пишет |
| `/sdd:intake` | описание story → proposal + дельты, остановка до design/tasks |
| `/opsx:update` | переработать proposal/specs после ревью, сохранив их связность |
| `/opsx:archive` | закрыть выкаченное изменение |

## Чего делать нельзя

- **Не пишите `design.md` и `tasks.md`**, даже если уверены в подходе. Это
  решение реализующего разработчика.
- **Не трогайте код в `src/*`.**
- **Не кладите внутренние спеки репозитория в `specifications`.** Локальному
  место в собственном `openspec/specs/` того репозитория.
- **Не архивируйте, пока не выкатились все потребляющие репозитории.**
